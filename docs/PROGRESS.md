## Решения, принятые по ходу

Сюда записывается только то, чего нет в `SPEC.md`, — выбор библиотеки,
обход ограничения, компромисс. Каждая запись: решение и почему.
Крупные решения, диктующие форму слоёв, живут в [`decisions/`](./decisions/).

### Расчёт

- **Даты — строки `YYYY-MM-DD`, арифметика без объекта `Date`.** Ни часовых поясов,
  ни скрытых часов; функции ядра остаются доказуемо чистыми.
- **Промежуточное произведение `сумма × дни` считается в `BigInt`.** Точность не
  зависит от масштаба сумм. `Math.round` в денежных расчётах не используется нигде.
- **Пересекающиеся отсутствия сливаются перед вычитанием.** База их запрещает (§11),
  но ядро не должно уметь вычесть один день дважды даже на грязных данных.
- **Вырожденный случай §4.4 разрешается цепочкой:** активные на дату заказа →
  задевшие период → все известные участники → ошибка, если участников нет вовсе.
- **`ADJUSTMENT` без участника распределяется поровну** между активными на дату
  операции. Подтверждено владельцем 14.08.2026, правило описано в `SPEC.md` §2.4.
- **Ядро выводит остаток фонда из таблиц `contributions` и `water_orders`,
  а не из журнала.** Строки `CONTRIBUTION` и `ORDER` в `fund_transactions` —
  для истории и аудита, а не источник расчёта, вопреки буквальному чтению §2.3.
- **Строки `OPENING` в журнал не пишутся вовсе.** Ядро берёт начальное сальдо
  из `fund_settings`; вторая запись превратила бы сумму журнала в неверное число.
  История стартового состояния живёт в `audit_log`, с пометкой `equal-split` (§4.2).

### Аутентификация

- **Вход по логину и паролю от администратора, код на почту удалён** — ADR-0004.
- **Сессия — подписанная cookie без таблицы в базе, но с моментом выдачи.**
  Отзыв — по участнику целиком: `users.sessions_valid_after` сдвигают бан и
  перевыпуск учётных данных, `isSessionCurrent` сверяет его с `iat` в cookie.
- **Пароль — scrypt с солью из `node:crypto`**, параметры записаны в строке
  отпечатка. Магическая ссылка — HMAC токена на серверном секрете, как раньше
  у кодов: токен длинный и случайный, медленный хеш не нужен.
- **Магическая ссылка входит по кнопке, а не на GET:** превью ссылок
  в Telegram открывает адрес заранее.
- **Отказы входа неразличимы, кроме бана после верного пароля.** Для
  несуществующего логина отпечаток всё равно считается — иначе видно по времени.
- **Лимит записей считается по `audit_log`**, а не по таблицам: у `absences`
  нет момента создания, а удаление записи не должно возвращать лимит.
  Индекс `audit_log(actor_id, action, created_at)` — в той же миграции.
- **Форма выдачи учётных данных — один `<form>` с полем `intent`**
  (`suggest` / `create`). React 19 сбрасывает поля после действия, поэтому
  введённое возвращается в состоянии и поля перечитывают `defaultValue` через
  `key={state.version}`.
- **Ошибки доступа бросаются как `GraphQLError`.** Обычный `Error` Yoga маскирует
  под `INTERNAL_SERVER_ERROR`, и клиент не отличает «войди заново» от «сервер упал».
  Поймано только живым запросом — ни типы, ни модульные тесты этого не видят.
- **`currentUser()` для серверных компонентов вынесен в `src/lib/auth/current-user.ts`
  и не реэкспортируется из `index.ts`:** он тянет `next/headers`, которыми нельзя
  пользоваться ни в тестах, ни в резолверах.

### Данные и API

- **Календарные даты пишутся и читаются только в UTC, метки времени — в зоне
  процесса.** Колонка `DATE` приходит полночью UTC, и локальные геттеры съезжают
  на день везде, кроме нулевой зоны. Момент времени — другое дело: заказ, внесённый
  в час ночи, в UTC попал бы во вчера.
- **Мемоизация пересчёта двойная:** `cache()` из React для серверных компонентов
  и промис в контексте для резолверов. Вне React-запроса `cache` вырождается
  в обычный вызов, а контекст создаётся на каждый запрос и работает всегда.
- **Пересечение отсутствий ищется запросом до вставки, а исключение базы ловится
  вторым рубежом.** Запрос даёт внятное сообщение с датами, `EXCLUDE USING gist`
  закрывает гонку. Опознаётся по коду PostgreSQL `23P01`.
- **Повторное удаление отсутствия возвращает `false`, а не ошибку.** Двойное
  нажатие кнопки — не отказ.
- **`Receipt.url` — ссылка на приложение (`/api/receipts/:id`), а не на хранилище.**
  Решение принято до выбора хранилища специально, чтобы вопрос №4 закрылся
  впоследствии без правки схемы и клиента. Он закрыт 22.09.2026 — байты лежат
  в базе ([ADR-0003](./decisions/0003-receipt-files-live-in-the-database.md)).
- **Ошибочно подтверждённый или отклонённый взнос повторно не рассматривается
  (`CONFLICT`).** Откат статуса означал бы правку следствия неизменяемой записи;
  исправление — только `ADJUSTMENT` (§2.4).
- **Скаляры проверяют значения сами, а не полагаются на резолверы.** `Money`
  возвращал `0` на дробный литерал, `Date` — пустую строку на нестроковый:
  запрос проходил, а в базу уезжала неправда. Резолвер можно забыть, границу — нет.
- **Выплатить больше текущего остатка нельзя** (`CONFLICT`): это не возврат,
  а новый долг, и почти всегда опечатка.
- **Последнего действующего администратора нельзя ни разжаловать, ни исключить.**
  §6.7 говорит только о разжаловании, но исключение оставляет панель без хозяина.
- **Не перечисленный в `setOpeningBalances` участник получает ноль**, а не сохраняет
  старое сальдо: сумма §4.2 берётся по всем участникам.
- **Фильтр журнала аудита по участнику работает в памяти** по выборке до 500 записей.
  Для офисной кассы запас огромный; на порядково больших объёмах — переносить в SQL.

### Фронтенд

- **Формы — на `useActionState` и `<form action>`, без `useEffect`.** Шаг входа
  выводится из состояния, а не хранится отдельно: два источника правды разъезжаются.
- **Данные и чистые функции не живут в модулях с `'use client'`.** Массив разделов
  лежал в клиентском модуле, оболочка его разворачивала — и все страницы участника
  отвечали 500: через клиентскую границу серверный компонент получает ссылку на
  клиентскую сущность, а не значение. Ни типы, ни тесты этого не видят.
- **Чистая логика экранов вынесена в `src/lib/view/`, форматирование — в
  `src/lib/format/`.** Иначе её нельзя проверить без базы и браузера, а компонент
  перестаёт быть тонким.
- **Графики — серверный inline-SVG без библиотеки.** Ни одной новой зависимости;
  подсказка при наведении — `<title>`, и каждое значение продублировано текстом,
  поэтому ничто не спрятано только в подсказку.
- **Палитра графиков проверена скриптом из навыка `dataviz`** против светлой и
  тёмной темы: полоса светлоты, порог цветности, протанопия и дейтеранопия,
  контраст — всё проходит. Пять цветов «любой с любым» не различимы, поэтому
  таймлайн разложен по дорожкам с подписями, а не свален в одно поле.
- **Отбор в таблицах — обычные `<form method="get">` и ссылки**, состояние в адресе:
  ноль клиентских компонентов и работа без JavaScript.
- **`export const dynamic = 'force-dynamic'`** на страницах приложения и админки:
  иначе `next build` пытается предрендерить их без сессии и без базы.
- **Девять разделов сгруппированы в пять.** В строку они не помещались, и
  шапка вырастала в два ряда: половина первого экрана уходила на навигацию.
  Близкие экраны собраны в разделы с вкладками (§6.11), вкладки рисует общий
  механизм — тот же, что раньше был отдельным `AdminNav`. Панель управления
  при этом переехала внутрь общей оболочки: раньше вход в неё отбирал у
  администратора всю остальную навигацию.
- **Группировка в интерфейсе не повторяет дерево маршрутов.** «Заказы» живут по
  адресу `/orders`, а принадлежат разделу «Касса» (`/fund`), поэтому раздел
  опознаётся перебором собственного адреса и адресов вкладок, а не сравнением
  префикса. Проверка префиксом молча подсвечивала бы не тот раздел.
- **Короткие подписи-описания пишутся без точки в конце.** Подзаголовок экрана
  или пояснение под формой — это название вещи, а не предложение, и точка там
  читается лишним знаком посреди интерфейса. Точки остаются у связного текста
  из нескольких предложений — объяснений и сообщений об ошибке.
- **Пустые обещания убраны с экрана взносов.** Колонка «Чек» показывала
  «без чека» в каждой строке, а поле чека было выключенным полем с
  объяснением, почему оно выключено: место занимали, сделать ничего было
  нельзя. Вернутся вместе с настоящими чеками (этап 6).
- **Таблица взносов растянута во всю ширину, всё в колонках по центру.**
  Выключка вправо у чисел на шести колонках расходилась с заголовками:
  свободное место браузер раздаёт всем, и края у столбцов разные.
- **Статус в таблице — бейджик со значком, а не один значок.** Тот же, что в
  ленте главной. Причина отказа живёт в подсказке по наведению; где причины
  нет, нет и подсказки — повторять голосом подпись, написанную рядом, незачем.
- **Объявление в ленте раскрывается плавно средствами CSS.** Анимируется
  `::details-content`, а не обёртка: закрываясь, браузер убирает содержимое
  из отрисовки мгновенно, и анимации закрытия не из чего строить. Высота
  идёт `0 → auto` благодаря `interpolate-size: allow-keywords` на `<html>`,
  `content-visibility` с `allow-discrete` откладывает исчезновение до конца
  перехода. Оба свойства пока только в Chrome и Edge; где их нет, раскрытие
  мгновенное — то есть прежнее.
- **Картинка объявления идёт во всю ширину плитки, и отступы поэтому внутри
  неё.** Содержимое `<details>` обрезается по своим краям — это цена анимации
  высоты, — и картинка, выведенная за них отрицательным полем, исчезла бы
  по бокам.
- **Закреплённое объявление вынуто из ленты в свой блок.** Закрепление
  означает «не тонуть», а лента отсортирована по дате: инструкция «как
  пользоваться кассой» уезжала под каждый новый заказ воды — делала ровно то,
  от чего её закрепляли. `buildFeed` закреплённых больше не отдаёт, их берёт
  `pinnedFeed`; показать в обоих местах значило бы показать одно объявление
  дважды, и второй раз — там, где оно тонет.
- **Значки статусов вынесены в `components/status-icons.ts`.** Сам
  `ContributionStatusIcon` помечен `'use client'` ради подсказки при
  наведении, а те же значки нужны ленте — серверному компоненту; через
  клиентскую границу компонент уехал бы ссылкой на клиентскую сущность. Та же
  причина, что у `nav-icons.ts`.
- **Чек открывается прямо из ленты, тем же диалогом, что в «Заказах».**
  Отдельного права на это не нужно: открыть чек может любой участник, деньги
  общие (§8.4). Событие возит метаданные чека — тип и идентификатор, — а не
  байты: байты лежат отдельной таблицей и отдаются по ссылке (ADR-0003).
  Бейджик-открывашка ростом со соседние, но вывернут наизнанку — сплошная
  заливка `--foreground` со светлым текстом: соседи стеклянные и только
  называют состояние, этот нажимается.
- **Мишень пальца растёт псевдоэлементом, а не самой кнопкой** (`.badge-tap`).
  Правило `@media (pointer: coarse)` поднимает любую кнопку до 44 пикселей и
  право в этом, но бейджик в плотном списке от этого растягивал строку втрое.
  Невидимый `::after` выходит за края кнопки: мишень есть, разметка не едет.
- **Крестик диалога светится кольцом только с клавиатуры.** Было `focus:`, а
  не `focus-visible:` — после нажатия мышью кольцо оставалось гореть, и оно же
  встречало при следующем открытии: Radix уводит фокус на крестик сам. В диалоге — только заголовок и файл,
  внизу «Открыть оригинал» и «Скачать»; `aria-describedby={undefined}`
  говорит, что описания нет намеренно, и снимает предупреждение о доступности.
- **В ленте у заказа видно число бутылей.** Цена одной воды меняется, и сумма
  без штук ни о чём не говорит. У заказов без счётчика штук нет вовсе: ноль
  там был бы неправдой, а не пустым местом.
- **Карточки главной собраны одной функцией `CardHead`.** Значок слева,
  заголовок, пояснение — иначе карточки с числом и карточки со списком
  читаются как куски разных экранов.
- **Подпись поля — стёклышко над ним, тем же приёмом, что выбранный раздел.**
  `.nav-pill` теперь стоит в двух местах, и обе поверхности проверяются одной
  строкой в `check:contrast`. Подпись блочная, а не строчная: у строчного
  элемента высота считается межстрочным интервалом родителя, а не собственным,
  и поэтому «Логин» с «Паролем» разъезжались при одинаковой разметке. Оба поля
  собраны одной функцией — разъехаться им больше нечем.
- **Касса и фонд помечены монетами, а не каплей.** Капля — знак приложения и
  вода; там, где речь о деньгах (раздел «Касса», заголовок «Фонда», плитка
  остатка на главной), значок должен говорить о деньгах.
- **Название приложения лежит в одном месте (`lib/view/app.ts`).** Оно стояло
  в четырнадцати заголовках вкладок подряд, и переименование означало
  четырнадцать правок, из которых одну обязательно забудут.
- **Связь с администратором есть в подвале каждого экрана, не только на
  входе.** Адрес берётся одной и той же функцией: два разных способа дописать
  схему однажды разошлись бы.
- **Схему адреса Telegram дописывает приложение.** `t.me/ivanov` без схемы —
  путь внутри сайта, и кнопка открывает свою же 404. Забыть схему в переменной
  окружения — норма, а не ошибка настройки, поэтому чинится это в коде.
- **Форма навигации одна, и выбирает её ширина экрана.** Боковая панель,
  переключатель формы, свёрнутое состояние, Ctrl + B и хранилище режима
  удалены целиком: три компонента, два модуля, скрипт в `<head>` и полсотни
  строк CSS обслуживали вопрос «каким меню вы предпочитаете пользоваться»,
  который интерфейс задавать не должен. Осталась верхняя полоса в один ряд и
  полоса значков у нижнего края телефона — `main-nav.tsx`, две функции на
  один список разделов.
- **Верхняя полоса не переносится на второй ряд ни на какой ширине.** Подпись
  под значком пробовали и отказались: место под строку находится и без этого,
  если убрать из полосы название приложения и имя участника. И то и другое
  повторяет соседний значок, а подпись раздела не повторяет ничего — уступают
  они. В самом крайнем случае полоса уедет по горизонтали.
- **Выбранный раздел выделен кромкой, бликом и тенью, а не цветом подложки.**
  Подложка проверена `check:contrast`; подкрасить её ради заметности значит
  вывести проверку из-под ног. Блик у `.nav-pill` симметричен — светлый по
  обеим кромкам, прозрачный посередине, — и заменяет блик стекла, а не ложится
  поверх: два светлых слоя подняли бы поверхность выше проверенной. Середина
  плитки, где блика нет, добавлена в `check:contrast` отдельным слоем; список
  цветов там сужен до подписи и кольца фокуса, потому что ничего другого в
  ссылке из одного слова не стоит.
- **Содержимое шапки стоит в контейнере содержимого (`max-w-6xl`), а стекло —
  во всю ширину.** Стекло здесь край экрана, но знак приложения и участник
  обязаны быть вровень с колонкой страницы: снаружи неё глазу не на что
  опереться.
- **Цифры фонда убраны из шапки.** Личный баланс и остаток фонда занимали
  середину полосы — то самое место, куда встали разделы, — и повторяли то, что
  главная показывает крупно и с объяснением. Вместе с ними из обеих оболочек
  ушёл вызов `fundState()`: шапке он был нужен, страницам — нет.
- **Нижняя полоса узкого экрана закреплена и знает про `safe-area`.** Место под
  неё держит отступ содержимого (`.nav-bottom-gutter`), и оба размера считаются
  от одного `env(safe-area-inset-bottom, 0px)`: на телефонах с жестовой полосой
  значки иначе упираются в неё, а последняя строка страницы — в значки.
- **Выход убран из навигации в профиль.** Действие редкое и необратимое, а
  место в одном ряду с ежедневными ссылками делало его случайно нажимаемым.
- **Переключатель темы — одна иконка на два состояния.** Значение `system`
  осталось в модели: оно решает первый визит, когда выбора ещё нет. Иконка
  показывает результат нажатия, а не текущее состояние: кнопка — это действие.
- **Адрес перехода после сохранения формы проверяется как ввод** (`isInternalPath`).
  Скрытое поле `redirectTo` приходит из браузера, и `//evil.example` в нём увёл
  бы человека с сайта после сохранения профиля.
- **Знакомство после первого входа переехало на `/welcome`.** Постоянный экран
  профиля живёт внутри оболочки `(app)`, а она же уводит безымянного участника
  на заполнение имени: оставь оба на `/profile` — редирект закольцевался бы.
- **В `scripts/smoke.ts` добавлен `import 'dotenv/config'`.** Скрипт работает вне
  Next.js, `.env` сам не читается, и проверка падала на `SESSION_SECRET не задан`.

### Оформление: вода и стекло (§12.1)

- **Прозрачность стекла подобрана по контрасту, а не по вкусу.** Первая попытка
  (карточка 76%, яркие пятна света) провалила AA в тёмной теме сразу в четырёх
  парах: стекло осветляет тёмную карточку, и приглушённый текст падал до 4.06:1.
  Правились подложка и пятна, а не палитра, — иначе разъехались бы контрастные
  соотношения, уже задокументированные в `globals.css`.
- **`npm run check:contrast` разбирает `globals.css`, а не хранит копию цветов.**
  Копия разошлась бы с темой в первый же день и уверенно проверяла бы
  несуществующие цвета. Скрипт считает худший случай: все три пятна света
  наложены друг на друга, блик взят в самой яркой точке.
- **Фон живёт на `<html>`, `<body>` прозрачен.** Фон корневого элемента
  распространяется на холст: он покрывает экран и не едет при прокрутке без
  `position: fixed` и без лишнего слоя в разметке. Фон на `<body>` закрасил бы
  воду собой — они не складываются.
- **Непрозрачная поверхность — значение по умолчанию, стекло надстраивается
  через `@supports`.** `backdrop-filter` без поддержки не деградирует сам:
  поверхность просто осталась бы полупрозрачной над пёстрым фоном — ровно тот
  случай, когда текст теряет контраст.
- **Значок раздела в навигации передаётся строкой, а не компонентом.**
  `main-nav.tsx` помечен `'use client'`, и компонент, вывезенный туда через
  границу, приехал бы ссылкой на клиентскую сущность — та же ловушка, что была
  со списком разделов. Разбор «ключ → значок» живёт в `components/nav-icons.ts`,
  на клиентской стороне границы.
- **Отклик на нажатие сделан классом `.press`, а не утилитой `active:scale-*`.**
  Утилиты Tailwind лежат слоем выше компонентов, и медиазапрос
  `prefers-reduced-motion` их бы не перекрыл.
- **Графики остались на непрозрачной поверхности `.plot-surface`.** Палитра §12
  проверена скриптом навыка `dataviz` против цвета карточки; на просвечивающей
  подложке проверка перестаёт что-либо гарантировать, а зазоры между
  соприкасающимися заливками рисуются цветом `--chart-surface` и на стекле
  выглядели бы швом.
- **Заголовки экранов вынесены в `PageHeader`.** Одна и та же шапка была
  скопирована на пяти страницах дословно.

### Объявления (§6.12)

- **Объявление не стало шестым типом события ленты.** Соблазн был: `EVENT_KINDS`
  уже описывает поток «что произошло». Но порядок типов закреплён за слотами
  палитры `--chart-1..5`, а пять цветов «любой с любым» уже неразличимы —
  шестой потребовал бы переделки проверенной палитры. Вдобавок `TimelineEvent`
  едет в графики и сводку за период, где событие без суммы бессмысленно.
  Поэтому — своя таблица, свой тип, своё место на экране.
- **Инструкция и новость — одна сущность с флагом `pinned`.** Отличаются они
  только сроком жизни: закреплённое не тонет, обычное уходит вниз по дате.
  Второй тип записи не дал бы ничего, кроме второго набора форм.
- **Непрочитанное — водяной знак `users.announcements_seen_at`, а не таблица
  связей.** Для полутора десятков человек и десятка сообщений таблица «кто что
  прочитал» стоила бы дороже пользы. Цена решения: отметить одно объявление
  прочитанным, оставив соседнее непрочитанным, нельзя.
- **Отметка ставится по самой свежей публикации, а не по `now()`.** Между
  чтением списка и записью может выйти новое объявление; `now()` погасил бы
  его непрочитанным, так и не показав. Отметка двигается только вперёд.
- **Отметку ставит отрисовка страницы `/notices`** — единственное место, где
  серверный компонент меняет состояние. Кнопка «отметить прочитанным» честнее,
  но нажимать её никто не станет, и значок горел бы вечно. Побочный эффект
  безопасен: он идемпотентен, денег не касается, а предзагрузка ссылки его не
  вызывает — страницы объявлены `force-dynamic` и заранее не отрисовываются.
- **Главная показывает непрочитанное, но отметку не ставит.** Иначе человек
  увидел бы заголовок на главной и никогда не прочёл бы текст.
- **Правка объявления не сдвигает дату публикации.** `published_at` — момент,
  когда команда впервые увидела сообщение; сдвинь его исправление опечатки —
  старая инструкция вспыхнула бы у всех как свежая новость.
- **Архив вместо удаления.** На запись ссылается журнал аудита, и физическое
  удаление стёрло бы то, на что он указывает.
- **Разметка текста — три правила и ни одной зависимости.** Абзац, `- ` и
  `1. `; разбор — чистая функция в `src/lib/view/announcements.ts`, отрисовка —
  настоящие `<p>`, `<ul>`, `<ol>`. Библиотека Markdown означала бы и новую
  зависимость, и `dangerouslySetInnerHTML` над тем, что ввели в поле формы.
- **`announcements(includeHidden: true)` от участника — отказ, а не пустой
  список.** Молчание одинаково отвечало бы и тому, кто пытается подсмотреть
  черновики, и тому, кто просто ошибся аргументом.
- **Картинка лежит в базе, а не в файловой системе и не в S3.** На момент решения
  ни хостинг (вопрос №3), ни хранилище чеков (вопрос №4, закрыт 22.09.2026,
  [ADR-0003](./decisions/0003-receipt-files-live-in-the-database.md)) не были
  выбраны, а решение должно было работать при любом ответе на оба: файловая
  система отваливается на Vercel,
  S3 требует несуществующих реквизитов. Для десятка картинок в офисной кассе
  база подходит целиком, а адрес выдачи ведёт на приложение — переезд не
  затронет ни схему, ни клиента.
- **Байты — отдельная таблица `announcement_images`.** Prisma выбирает все
  колонки, если не попросить иначе, и `BYTEA` внутри `announcements` означал бы,
  что список объявлений на каждом экране вычитывает мегабайты, которые ему
  не нужны. Сюда ходит ровно один обработчик.
- **Тип картинки определяется по сигнатуре файла, а не по `Content-Type`
  из формы.** Заголовок от браузера — такой же ввод, как и всё прочее: страница
  HTML, названная `image/png` и отданная обратно с этим заголовком, выполнилась
  бы в чужом браузере. Заодно из заголовка достаются размеры, и разметка
  резервирует место под картинку до её загрузки.
- **Картинка — отдельная мутация, а не поле в `AnnouncementInput`.** Там
  «поле не прислали» и «поле пустое» пришлось бы различать, чтобы правка текста
  не сносила картинку молча.
- **Файл проверяется в серверном действии до создания объявления.** Иначе
  непринятая картинка оставляла бы за собой уже сохранённую запись без неё.
  Правило при этом не удваивается: `inspectImage` один на действие и резолвер.
- **Показывается обычным `<img>`, а не `next/image`.** Оптимизатор ходит за
  картинкой отдельным запросом без cookie сессии, а выдача закрыта входом —
  и получал бы 401 вместо картинки.
- **`serverActions.bodySizeLimit` поднят до 3 МБ.** Умолчание — 1 МБ, и форма
  с картинкой упиралась бы в него раньше, чем в собственную проверку размера:
  человек видел бы «Body exceeded 1 MB» вместо внятного отказа.

Устройство хранения и выдачи — в [ADR-0003](./decisions/0003-receipt-files-live-in-the-database.md).
Здесь — то, чего в нём нет.

- **Чек к поставке обязателен, а колонка `water_orders.receipt_id` — нет.** Требование
  держится схемой GraphQL (`receiptFileId: ID!`), а не разметкой формы; `NULL` в базе
  остаётся ради девяти заказов, заведённых до появления правила. Решение владельца
  от 22.09.2026: прозрачность важнее удобства ввода.
- **Чек загружается отдельной мутацией до создания заказа.** `createWaterOrder` требует
  готовый `receiptFileId`, поэтому порядок именно такой; неудачное создание заказа
  оставляет ни к чему не привязанный чек — он никому не виден (§8.4) и виден в аудите.

### Инфраструктура

- **ESLint зафиксирован на 9.39.5:** `eslint-plugin-react` из состава
  `eslint-config-next@16.3.0` падает на ESLint 10.
- **Prisma 7 требует driver adapter** — добавлен `@prisma/adapter-pg`, конфигурация
  в `prisma.config.ts`. Клиент генерируется в `src/generated/prisma` и в git не
  попадает; его восстанавливает `postinstall`.
- **Клиент Prisma создаётся лениво, через прокси.** `next build` обходит модули
  маршрутов, и клиент, создаваемый на импорте, требовал бы базу во время сборки.
- **У `login_codes` добавлен суррогатный `id BIGSERIAL`** — в §11 первичного ключа
  не было, а Prisma требует уникальный идентификатор у каждой модели.
- **`EXCLUDE USING gist`, CHECK-ограничения и расширения `citext`/`btree_gist`**
  вынесены в написанную руками миграцию `prisma/migrations/00000000000000_init/`.
- **Правило «изменения схемы правим прямо в начальной миграции» отменено
  владельцем 28.08.2026.** Оно держалось на том, что базы нет нигде и её не жаль
  пересоздать; база разработки давно живёт с данными, и терять их ради двух
  таблиц дороже, чем завести миграцию. С этого дня любое изменение схемы —
  **новая** миграция, начальная не трогается. Дело не только во вкусе: её
  контрольная сумма записана в `_prisma_migrations`, и правка файла ломает
  `migrate deploy` расхождением сумм. Первой по новому правилу легла
  `20260828000000_announcements`.
- **В codegen добавлены мапперы на модели Prisma.** Без них резолвер обязан вернуть
  сразу весь граф вместо строки таблицы.
- **Тесты ядра лежат в `tests/`, а не рядом с исходниками**, поэтому в
  `vitest.config.ts` добавлен отдельный шаблон включения.
- **`.claude/worktrees/` игнорируется git и ESLint:** рабочие копии субагентов —
  полные клоны проекта со своими сборками, линтер на них захлёбывался.
- **База для разработки — `docker-compose.yml`, порт 5433.** Реквизиты совпадают
  с `.env.example`. Порт нестандартный: 5432 на машине занят чужим контейнером,
  останавливать который ради нашего незачем.
- **`npm run smoke` — дымовая проверка на живой базе.** `npm test` не отрисовывает
  ни одной страницы, и отказ 500 на всех экранах участника нашёлся только запросом
  настоящей страницы. Скрипт проверяет инвариант, права и отрисовку всех маршрутов.

## Долги

Что сделано, но не проверено или отложено.

- **Экраны просмотрены глазами частично.** Десять экранов сняты в обеих темах
  headless-браузером на живых данных (главная, вход, дашборд, фонд, взносы,
  отсутствия, профиль, две вкладки админки, главная на 390px) и разобраны.
  Не проверено глазами: узкий экран на всех остальных страницах, ландшафтная
  ориентация, крупный системный кегль, режимы `prefers-reduced-transparency`
  и `forced-colors` — в них поверхности должны становиться непрозрачными,
  правила написаны, но не наблюдались.
- **Сквозные сценарии форм не прогонялись.** Подача взноса → подтверждение →
  изменение баланса проверено через резолверы, но не через настоящую отправку
  формы в браузере. То же для отметки отсутствия и заполнения профиля.
- **Экраны объявлений не смотрели глазами.** Миграция к живой базе применена,
  но ни `/notices`, ни `/admin/notices` в браузере не открывались, и
  `npm run smoke` на них не прогонялся. Отдельно не проверялась загрузка
  настоящего файла: разбор формата покрыт тестами на собранных вручную
  заголовках, но путь «выбрал файл в браузере → картинка на экране» целиком
  не проходился ни разу.
- **Чек к заказу воды (§6.5, §8.4) не смотрели глазами вовсе.** Миграция
  `20260922120000_receipt_files` к живой базе не применена: сессия агента её не
  трогала, чтобы не задеть данные владельца. Форма поставки, обязательность
  чека, предпросмотр PDF и PNG до отправки, кнопка чека в списке заказов,
  доступ участника к чужому и своему заказу, отказ без чека — всё это проверено
  тестами на подставном Prisma, но не настоящей отправкой формы в браузере и не
  `npm run smoke`. Ветка `feat/order-receipts` не влита в `main`.
- **`.env` в рабочей копии заводится вручную.** Файл в git не попадает, а
  worktree — отдельная копия репозитория, поэтому в новой копии его нет и
  приложение падает на `SESSION_SECRET` ещё до обращения к базе.
- **Ограничение сложности запроса не сделано.** §10.3 обещает `graphql-depth-limit`
  и лимит стоимости — их нет. За логином терпимо, до публикации закрыть.
- **Server Actions не покрыты тестами** — они тянут `next/headers`. Риск ограничен
  разбором формы: все правила живут в резолверах, а те протестированы.
- **`entered_by_admin` наружу через GraphQL не отдаётся.** Админ-панель читает флаг
  через слой данных; если он понадобится на общих экранах — добавить поле в типы.
- **Начальные сальдо остались в модели после отмены импорта.** Механизм вшит в ядро
  с тестами и используется админ-панелью, так что выкорчёвывать его — отдельная
  задача, а не попутная правка.

# Журнал архитектурных решений

Здесь лежат ADR — Architecture Decision Records. Каждый файл фиксирует одно
решение: что выбрали, из чего выбирали, почему и чем за это платим.

Смысл формата в том, что через полгода вопрос «зачем мы вообще взяли эту штуку»
задаст либо новый человек, либо ты сам. Код показывает, *как* сделано, но
никогда не показывает, *почему не сделано иначе*, — и без записи ответ
восстанавливается только по памяти, то есть неверно.

## Когда заводить ADR

Решение попадает сюда, если верно хотя бы одно:

- отменить его дорого — придётся переписывать не файл, а слой;
- оно диктует, как пишутся другие части (GraphQL диктует форму резолверов,
  выбор Prisma диктует форму слоя данных);
- при обсуждении был реальный выбор, и отвергнутые варианты не очевидны;
- кто-то со стороны, посмотрев на код, справедливо спросит «а зачем так?».

Мелкие решения сюда **не пишутся**. Для них есть раздел «Решения, принятые
по ходу» в [`../PROGRESS.md`](../PROGRESS.md): выбор библиотеки-однодневки, обход
ограничения инструмента, компромисс на один файл. Граница простая: ADR — про
то, что переживёт этап; PROGRESS — про то, что переживёт сессию.

Как распределяются документы:

| Документ | О чём |
|---|---|
| [`../BRIEF.md`](../BRIEF.md) | Зачем продукт и кому |
| [`../SPEC.md`](../SPEC.md) | Что приложение делает: модель, схема, экраны |
| `docs/decisions/` | Почему оно устроено именно так |
| [`../PROGRESS.md`](../PROGRESS.md) | Где работа сейчас и что решили по ходу |

Если ADR противоречит `SPEC.md`, правится тот из них, который отстал, — и
в том же коммите. Два разошедшихся документа хуже одного отсутствующего.

## Формат

Имя файла: `NNNN-short-title-in-english.md`, номер сквозной и не переиспользуется
даже после отмены решения. Номер — это адрес: на него ссылаются из кода
и из других ADR.

Разделы: статус и дата, контекст, движущие соображения, рассмотренные варианты
с их ценой, решение, последствия (и хорошие, и плохие), границы решения,
как проверяется соблюдение, когда решение пора пересмотреть.

Последние три раздела в классическом шаблоне Найгарда отсутствуют, но без них
запись быстро превращается в мемуары. «Границы» отвечают на вопрос, где решение
не действует; «проверка» — чем подтверждается, что правило живо, а не забыто;
«когда пересматривать» задаёт условие, при котором запись стоит перечитать.

## Статусы

| Статус | Значение |
|---|---|
| Предложено | Обсуждается, менять код по нему рано |
| Принято | Действует, код обязан ему соответствовать |
| Отклонено | Рассматривалось и отвергнуто; запись остаётся ради причины |
| Устарело | Потеряло смысл вместе с задачей, ничем не заменено |
| Заменено ADR-NNNN | Отменено другим решением; ссылка обязательна |

**Принятый ADR не переписывается задним числом.** Передумали — заводится новая
запись со статусом «Заменено», а старая остаётся как есть. Ровно по той же
причине, по какой неизменяем журнал операций фонда (`CLAUDE.md`, правило 4):
история, которую можно молча поправить, ничего не доказывает.

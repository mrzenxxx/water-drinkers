## Контекст

WaterDrinkers — учёт офисной кассы на воду для полутора десятков человек.
Нагрузка ничтожная, состав пользователей известен поимённо, экранов меньше
десяти. По одним лишь техническим требованиям хватило бы чего угодно.

Но у проекта есть вторая, явно заявленная цель: **разобраться с GraphQL на
живой предметной области, а не на учебном примере**. Это осознанный выбор
владельца, и он меняет условие задачи: инструмент выбирается не только по
критерию «дешевле всего решает», но и по критерию «даёт ли встретить настоящие
проблемы этого подхода».

Предметная область под это подошла удачнее, чем ожидалось:

- **пересекающиеся срезы одних данных.** Главной (§6.1) нужен один баланс
  и остаток фонда. Экрану «Фонд» (§6.4) — те же балансы, но с полной
  построчной раскладкой по каждому заказу. Это один тип с разным объёмом;
- **естественный N+1.** `contributions { user { firstName } }` на двести
  взносов без батчинга даёт двести походов в базу. Ловушка возникает сама,
  её не приходится подстраивать;
- **деньги.** Правило 2 (`CLAUDE.md`) запрещает плавающую точку в денежных
  расчётах. Появляется настоящая задача для скаляра — типа, который проверяет
  значение на границе, а не полагается на договорённость;
- **будущие потребители.** Этап 8 — Telegram-бот и Mini App, этап 7 —
  ИИ-помощник. Обоим нужны те же данные, что и вебу.

## Движущие соображения

1. Один контракт на все будущие клиенты: веб, Telegram, помощник, внешние скрипты.
2. Сквозная типизация от базы до компонента; расхождение обязано ловиться компилятором.
3. Права доступа описаны в одном месте, а не рассыпаны по обработчикам.
4. Инструмент должен позволить столкнуться с N+1 и решить его как положено — учебная цель.
5. Цена сопровождения не должна превышать пользу: команда — один человек.

## Рассмотренные варианты

### A. Набор REST-эндпоинтов

Дёшево, знакомо, кешируется по HTTP из коробки.

Цена: под два разных объёма одних и тех же балансов — либо два эндпоинта,
либо тяжёлый ответ на экране, где нужно одно число. Типизация клиента —
ручная и разъезжается молча. Учебной цели не даёт вовсе.

### B. tRPC

Идеальная типизация без кодогенерации, минимум церемоний.

Цена: контракт существует только внутри TypeScript. Telegram-бот на другом
языке или внешний потребитель остаются ни с чем — а это прямо запланировано
этапом 8. Учебной цели тоже не отвечает.

### C. Только Server Actions, без API как такового

Самый короткий путь для веба: формы вызывают серверные функции, чтение —
серверными компонентами. Ровно то, что React 19 и предлагает.

Цена: наружу не торчит ничего. Telegram и помощнику пришлось бы дописывать
отдельный слой, то есть принимать это же решение, но позже и под давлением.

### D. GraphQL поверх Yoga — **выбрано**

Один эндпоинт, форму ответа задаёт клиент, схема служит исполняемым контрактом
и одновременно документацией.

Цена перечислена ниже честно и полностью: она не нулевая.

## Решение

**Контракт API проекта описывается схемой GraphQL. Сервер — GraphQL Yoga,
встроенный в Next.js как Route Handler.**

Устройство:

```
src/graphql/schema.graphql      контракт: типы, запросы, мутации (SPEC §10.2)
   ↓ npm run codegen
src/graphql/generated/          типы резолверов и клиента
src/graphql/resolvers/          как получить каждое поле
src/graphql/loaders/            DataLoader: батчинг походов в базу
src/graphql/context.ts          кто вошёл, база, лоадеры, мемоизация пересчёта
src/graphql/scalars.ts          Date, DateTime, Money, JSON
src/app/api/graphql/route.ts    Yoga внутри Next.js
```

Сопутствующие решения, принятые вместе с этим:

| Аспект | Решение |
|---|---|
| Типизация | GraphQL Code Generator, результат коммитится — сборка не зависит от прогона codegen |
| N+1 | DataLoader на `User`, `Receipt`, `WaterOrder` и связи участника; лоадеры создаются на каждый запрос |
| Авторизация | Проверка роли в резолверах через контекст (`requireUser`, `requireAdmin`) |
| Ошибки | Типизированные коды в `extensions.code`, не строки сообщений |
| Загрузка файлов | Вне GraphQL: `POST /api/upload` → `fileId` |
| Песочница | GraphiQL на `GET /api/graphql` — она же документация API |

### Резолвер — функция на поле, а не на запрос

Это главное, что отличает GraphQL от «ручки, возвращающей JSON», и из чего
следует всё остальное. Yoga обходит дерево запрошенных полей и на каждое зовёт
свою функцию: `Query.balances` вернул восемь балансов — для каждого зовётся
`Balance.user`, затем `Balance.breakdown`, затем на каждой доле `OrderShare.order`.

Родитель поля при этом **не обязан быть строкой таблицы**. В `codegen.ts`
прописаны мапперы: `User` — строка Prisma, а `Balance`, `BalanceBreakdown`
и `OrderShare` — результат чистого ядра расчёта из `src/lib/calc/`. Баланса
в базе нет вовсе, он вычисляется; схема этого различия не показывает, и
правильно делает — клиенту всё равно, откуда взялось число.

### Пример: один тип, два объёма

Главная (§6.1):

```graphql
query Home {
  fund { balance }
  balances { amount owes user { firstName lastName } }
}
```

Экран «Фонд» (§6.4) — тот же тип `Balance`, полная раскладка:

```graphql
query Breakdown {
  fund { balance balancesSum isConsistent }
  balances {
    amount
    user { email }
    breakdown {
      openingBalance contributionsTotal expensesTotal settlementsTotal adjustmentsTotal
      orderShares { daysPresent totalPersonDays share order { orderedAt amount supplier } }
    }
  }
}
```

Ровно эта пара запросов и была причиной выбора: в REST под неё нужны либо две
ручки, либо тяжёлый ответ там, где нужно одно число.

### Пример: мутация и типизированная ошибка

```graphql
mutation { confirmContribution(id: "…") { id status } }
```

Мутация возвращает обновлённую сущность, а не «ок». Отказ приходит с кодом
в `extensions.code` — `FORBIDDEN`, `CONFLICT`, `ABSENCE_OVERLAP`,
`BAD_USER_INPUT`, — и клиент решает по коду, а не по тексту сообщения.

## Последствия

### Положительные

- **Расхождение схемы и кода ловит компилятор.** Переименовал поле — `tsc`
  показал все места, где оно использовалось.
- **Документация не устаревает,** потому что она и есть схема: GraphiQL
  на `GET /api/graphql` показывает типы, обязательность полей и результат
  каждой мутации.
- **Права видны в одном месте.** `pendingContributions` и `auditLog` помечены
  «только ADMIN» прямо в схеме и проверяются в резолверах через контекст.
- **Готовый контракт для этапов 7 и 8.** Помощнику и Telegram Mini App
  серверную часть дописывать не придётся.
- **N+1 решён и измерен, а не «учтён».** Цифры — в разделе «Проверка».

### Отрицательные

- **HTTP-кеширование не работает:** всё идёт `POST`-ом на один URL, промежуточные
  кеши бессильны. Для приложения на полтора десятка человек это безразлично,
  для публичного API было бы существенно.
- **Ограничение сложности запроса не даётся бесплатно.** Клиент вправе
  запросить дерево, которое положит базу; глубину и стоимость надо ограничивать
  отдельно (`graphql-depth-limit`, §10.3) — **пока не сделано**.
- **Загрузка файлов вне протокола.** Чек грузится обычным `POST /api/upload`,
  в GraphQL уезжает только `fileId`. Это нормальная практика, но лишний путь.
- **Слой кодогенерации** — ещё один шаг в сборке и ещё один способ забыть его
  выполнить. Смягчено тем, что результат коммитится.
- **Церемоний больше, чем требует задача.** Честно: для пятнадцати человек
  в офисе REST хватило бы за глаза. Оправдано учебной целью и этапом 8,
  а не сегодняшней нагрузкой.

### Нейтральные

- Скаляры `Date`, `DateTime`, `Money`, `JSON` определяются вручную — в GraphQL
  их нет в стандарте.
- Ошибки доступа обязаны бросаться как `GraphQLError`: обычный `Error` Yoga
  маскирует под `INTERNAL_SERVER_ERROR`, и клиент не отличает «войди заново»
  от «сервер упал». Обнаружено живым запросом, ни типы, ни модульные тесты
  этого не видят.

## Границы решения

**Серверные компоненты не ходят по HTTP в собственный `/api/graphql`.** Они
зовут слой данных напрямую (`SPEC.md` §12а, `CLAUDE.md`). Сеть внутри одного
процесса — чистые потери: сериализация, разбор, лишний обход дерева резолверов
ради данных, которые лежат в двух функциях отсюда.

Практическое следствие, которое стоит понимать трезво: **на большинстве экранов
GraphQL как транспорт не участвует вовсе.** Работают его типы, схема как
контракт и резолверы как описание прав. Сам HTTP-эндпоинт остаётся для
клиентских компонентов, Telegram и внешних потребителей.

Мутации из интерфейса идут через Server Actions, а не через HTTP-запрос
к своему же GraphQL. Разделение получается такое:

| Что | Чем |
|---|---|
| Чтение для страницы | Серверный компонент → слой данных |
| Запись из формы | Server Action → тот же слой данных |
| Чтение и запись извне | GraphQL по HTTP |

Обе половины обязаны звать **одни и те же функции** `src/lib/data/`. Это не
эстетика: два пути к одному числу неминуемо разъезжаются, и тогда `isConsistent`
перестаёт что-либо доказывать.

Отдельно: **Server Action — такая же публичная точка входа, как эндпоинт.**
То, что кнопку «Подтвердить» видно только администратору, не значит ничего.
Права проверяются внутри действия, ровно как резолвер зовёт `requireAdmin`.
Скрытая кнопка — не защита.

## Проверка соблюдения

Решение считается живым, пока выполняется всё перечисленное:

- `npm run codegen` не порождает изменений на чистом дереве — схема и типы сошлись;
- `npm run typecheck` зелёный: резолвер, вернувший не то поле, не компилируется;
- тесты `tests/graphql/loaders.test.ts` держат батчинг под счётом запросов,
  а не на глаз:
  - восемь взносов восьми участников читают участников **двумя** запросами
    вместо девяти (первый — проверка прав, второй — батч на всех авторов);
  - девять участников с их отсутствиями и взносами — **по одному запросу
    на связь**, а не на участника;
  - участник, попавший в ответ трижды, читается **один раз**;
  - баланс, спрошенный тремя разными полями, вызывает **один** пересчёт;
- живой прогон против PostgreSQL (14.08.2026): все запросы §10.2 отработали,
  права отдали `UNAUTHENTICATED` и `FORBIDDEN`, 15 проверок мутаций прошли,
  инвариант §5 сошёлся копейка в копейку.

### Что эта проверка уже нашла

Написание настоящего ADR вскрыло дыру в скалярах, и она стоит того, чтобы
остаться здесь записанной: разбор границ типов — не формальность.

Скаляр `Money` объявлял «целое число копеек», но сам ничего не проверял:
`parseValue` сводился к `Number(value)`, а `parseLiteral` разбирал только
`Kind.INT` и на дробный литерал **молча возвращал `0`**. Скаляр `Date` так же
молча отдавал пустую строку на нестроковое значение. Целость держалась только
на резолверах — то есть на памяти того, кто пишет очередной резолвер.

Пока суммы проходили через `requirePositiveMoney`, это ничем не грозило. Но
мутации со знаковыми суммами (`createAdjustment`, `settleParticipant`) под ту
проверку не попадают, и там яма была открыта настежь: «250.50» вместо 25050
копеек уехало бы в базу нулём, а инвариант §5 разошёлся бы без единой ошибки
в логах.

Исправлено в `e9c74e3`: проверка перенесена на границу — там ей и место.
Ни один скаляр больше не «чинит» негодное значение молча, негодный ввод
отвергается с кодом `BAD_USER_INPUT`, а негодный вывод — как ошибка сервера,
потому что это баг, а не действие клиента.

**Общее правило, которое из этого следует:** резолвер можно забыть, границу —
нет. Проверка, которую можно обойти, добавив новый резолвер, проверкой
не является.

## Когда пересматривать

- Если этап 8 отменится, а других потребителей API не появится — исчезнет
  главный практический довод, и останется только учебный.
- Если схема начнёт расти быстрее, чем экраны, — признак, что контракт
  обслуживает сам себя.
- Если появится публичный доступ — сначала ограничение сложности запроса,
  иначе один запрос кладёт базу.

# ADR-0002. Запись идёт через Server Actions, которые зовут резолверы в процессе

**Статус:** Принято
**Дата:** 14.08.2026
**Связано с:** [ADR-0001](./0001-graphql-yoga-as-api-contract.md), `CLAUDE.md` (React 19, правила 1 и 4), `SPEC.md` §12а

## Контекст

К этапу 5 у приложения два входа для изменения данных. Первый — `POST /api/graphql`:
им пользуются клиентские компоненты, GraphiQL и, в будущем, Telegram (§14, этап 8).
Второй — формы на экранах: React 19 отправляет их прямо в серверную функцию,
без единой строчки клиентского JavaScript.

Вопрос не в том, какой вход оставить, — нужны оба. Вопрос в том, **где живут
правила**: проверка прав, транзакция, запись в журнал аудита, сброс мемоизации
пересчёта и, главное, инвариант §5.

Цена ошибки здесь выше обычной. Инвариант «Σ балансов == остаток фонда» — не
пожелание, а первое незыблемое правило проекта, и держится он на том, что каждое
изменение денег проходит через один и тот же код. Два пути, написанных по
отдельности, разойдутся не сразу и не громко: сначала в одном забудут запись
`fund_transactions`, потом в другом — сброс кеша, и приложение начнёт показывать
числа, которые не сходятся, продолжая уверять, что сходятся.

## Движущие соображения

- **Одна реализация правил.** Расхождение двух путей ломает §5 тихо.
- **Формы должны работать без JavaScript.** `<form action>` — обычная HTML-форма;
  клиентский `fetch` так не умеет.
- **Сеть внутри процесса — чистые потери.** HTTP-запрос приложения к самому себе
  стоит сериализации, нового соединения и второго чтения cookie (§12а).
- **Права проверяются на сервере, а не скрытием кнопки.** Server Action — такая же
  публичная точка входа, как эндпоинт: адрес действия уезжает в разметку.

## Рассмотренные варианты

| Вариант | Цена |
|---|---|
| **Действие пишет в Prisma само** | Быстро писать, дорого жить: права, аудит, транзакция и сброс пересчёта дублируются в каждом действии. Именно тот случай, когда §5 ломается молча. |
| **Действие делает `fetch` к своему же `/api/graphql`** | Правила не дублируются, но каждый вызов — лишний HTTP внутри одного процесса, плюс cookie приходится пробрасывать руками. Сеть ради вызова функции. |
| **Отказаться от Server Actions, всё писать клиентским GraphQL** | Один вход, но формы перестают работать без JS, и на каждую мутацию появляется ручная сборка запроса, разбор `errors[0]` и своя инвалидация кеша. |
| **Действие зовёт резолвер напрямую в процессе** ✅ | Требует собрать контекст резолвера вне HTTP-запроса — единственная неочевидная часть. Взамен: правила в одном месте, ноль сети, формы работают без JS. |

## Решение

Server Action собирает контекст (`src/lib/actions/runtime.ts`, `admin.ts`) и вызывает
**тот же резолвер**, который обслуживает HTTP-эндпоинт. Действие отвечает только за
разбор `FormData`, перевод результата в состояние формы и `revalidatePath`.

Правила остаются там, где были: проверка прав — `requireUser` / `requireAdmin`,
транзакция и запись в `fund_transactions` — в резолвере, аудит — `writeAudit`
в той же транзакции, пересчёт — `ctx.invalidateFundState()`.

Чтение устроено зеркально и описано в ADR-0001: серверные компоненты берут данные
из слоя `src/lib/data/`, тоже без HTTP к себе.

## Последствия

**Хорошие.**
Правила мутации написаны один раз и покрыты интеграционными тестами на подставном
Prisma — те же тесты защищают оба входа. Форма отправляется без гидратации.
Мутация не платит ни за сериализацию, ни за соединение. Коды ошибок (`CONFLICT`,
`ABSENCE_OVERLAP`, `FORBIDDEN`) одни и те же на экране и в API.

**Плохие.**
Контекст резолвера приходится собирать вручную вне HTTP-запроса — это отдельный
модуль, который легко забыть обновить при изменении контекста. Сами действия
тестами не покрыты: они тянут `next/headers`. Риск ограничен разбором формы, но он
есть. И граница «серверное — клиентское» становится тонкой: импорт из модуля
с `'use server'` или `'use client'` тащит за собой лишнее, вплоть до попадания
Prisma в браузерный бандл (поэтому состояние формы вынесено в отдельный файл).

## Границы решения

Решение действует на **запись**. Чтение — предмет ADR-0001.

Оно не отменяет HTTP-эндпоинт: клиентские компоненты, GraphiQL и внешние
потребители работают по-прежнему через `/api/graphql`. Экран входа сознательно
оставлен на клиентском `fetch` — он клиентский по природе (§7, два шага с кодом).

Оно **не** разрешает действию обходить резолвер «ради одного простого поля».
Простых полей в денежном приложении не бывает: изменение, не прошедшее через
резолвер, не попадёт ни в аудит, ни в журнал фонда.

## Как проверяется соблюдение

- Интеграционные тесты резолверов (`tests/graphql/`) — единственное место, где
  описано поведение мутаций; если действие обойдёт резолвер, тесты этого не
  заметят, а вот `npm run smoke` на живой базе покажет несходящийся инвариант.
- `npm run smoke` проверяет §5 на настоящих данных и отрисовку каждой страницы.
- Ревизия импортов: в `src/lib/actions/` не должно быть обращений к `prisma`
  напрямую, кроме сборки контекста.

## Когда пересматривать

- Если появится потребитель, которому нужна мутация **без** резолвера — например,
  фоновая задача или импорт: тогда правила придётся опустить на уровень ниже,
  в слой данных, и ADR заменяется новым.
- Если Next.js изменит модель Server Actions так, что сборка контекста вне
  запроса перестанет быть возможной.
- Если действий станет столько, что ручная сборка контекста начнёт разъезжаться
  с настоящим контекстом Yoga: это сигнал вынести её в общий модуль с тестом.

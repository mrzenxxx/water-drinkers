## 2. Доменная модель

### 2.1 Сущности

| Сущность | Назначение |
|---|---|
| **Участник** (`User`) | Сотрудник офиса. Имеет период членства `[joinedAt, leftAt)` и начальное сальдо. |
| **Взнос** (`Contribution`) | Платёж участника в фонд. Проходит модерацию администратором. |
| **Заказ** (`WaterOrder`) | Покупка воды. Списание из фонда. |
| **Отсутствие** (`Absence`) | Период отсутствия участника — отпуск или больничный. Исключается из расчёта дней потребления. |
| **Фонд** (`Fund`) | Синглтон: начальное сальдо, дата начала учёта, размер типового взноса. |
| **Чек** (`Receipt`) | Файл-подтверждение и результат его распознавания. |
| **Запись аудита** (`AuditEntry`) | Кто, что и когда изменил. |

### 2.2 Денежные величины

**Все суммы хранятся в копейках, целыми числами (`BIGINT`).** Числа с плавающей точкой в проекте запрещены: инвариант §5 требует точного равенства, а `0.1 + 0.2 !== 0.3`. Конвертация в рубли — только на слое представления.

### 2.3 Операции фонда

Единый журнал `FundTransaction` — источник истины для остатка фонда:

| Тип | Знак | Источник |
|---|---|---|
| `OPENING` | + | Стартовое состояние, заданное администратором |
| `CONTRIBUTION` | + | Подтверждённый взнос участника |
| `ORDER` | − | Заказ воды |
| `SETTLEMENT` | − | Выплата остатка выходящему участнику |
| `ADJUSTMENT` | ± | Ручная корректировка администратора (обязателен комментарий) |

Ни одна запись журнала не удаляется и не редактируется. Это условие доверия: если
любую строчку можно втихую поправить задним числом, прозрачность приложения ничего
не стоит. Ошибка гасится **встречной записью**, и в истории видно и ошибку, и её
исправление.

### 2.4 Как исправлять ошибки

| Что произошло | Чем гасится |
|---|---|
| Заказ вбит на неверную сумму | Встречная запись `ORDER` на разницу. Она разойдётся по дням присутствия так же, как исходный заказ. |
| Подтверждён взнос, которого не было | `ADJUSTMENT` **с указанием участника** — адресат очевиден. |
| В фонде обнаружились деньги неизвестного происхождения | `ADJUSTMENT` **без участника** — см. правило ниже. |

**Корректировка без участника делится поровну** между участниками, активными на дату
операции (округление по §4.6). Иначе она изменила бы остаток фонда, не изменив ничей
личный баланс, и сломала бы инвариант §5.

В интерфейсе поле участника заполняется по умолчанию: «не знаю, чьи деньги» должно
быть осознанным выбором с обязательным комментарием, а не путём наименьшего
сопротивления.

### 2.5 Словарь

Термины в коде английские, в разговоре русские. Соответствие:

| В коде | По-русски | Что это |
|---|---|---|
| `User` | Участник | Сотрудник, который скидывается на воду |
| `Contribution` | Взнос | Платёж участника в фонд |
| `WaterOrder` | Заказ | Покупка воды, списание из фонда |
| `Absence` | Отсутствие | Отпуск или больничный |
| `Fund` | Фонд | Общая касса |
| `FundTransaction` | Операция | Строка неизменяемого журнала фонда |
| `OPENING` | Начальное сальдо | Стартовый баланс на дату начала учёта |
| `SETTLEMENT` | Выплата | Возврат остатка выходящему участнику |
| `ADJUSTMENT` | Корректировка | Исправление ошибки учёта встречной записью |
| `Balance` | Баланс | Взносы участника минус его доля расходов |
| `OrderShare` | Доля в заказе | Сколько с участника пришлось на конкретный заказ |

## 3. Роли и права

| Действие | Участник | Администратор |
|---|:---:|:---:|
| Видеть фонд, все взносы, все заказы, все балансы | ✅ | ✅ |
| Добавить свой взнос с чеком | ✅ | ✅ |
| Указать свой отпуск | ✅ | ✅ |
| Подтвердить / отклонить взнос | ❌ | ✅ |
| Внести заказ воды | ❌ | ✅ |
| Добавить / деактивировать участника, выдать логин и пароль | ❌ | ✅ |
| Ограничить участника: только просмотр или закрыть вход | ❌ | ✅ |
| Задать начальные сальдо, корректировку, выплату | ❌ | ✅ |
| Читать объявления | ✅ | ✅ |
| Публиковать и править объявления | ❌ | ✅ |
| Задать вопрос Помощнику | ✅ | ✅ |

Приложение полностью прозрачно: участник видит всё, что видит администратор. Разница только в праве изменять.

**Ограничения участника** (`users.restriction`) задаёт администратор, и для
администратора их нет:

- **Только просмотр** (`MUTED`). Участник видит всё, но не может подавать
  взносы, отмечать и удалять отсутствия, загружать чеки и менять профиль.
  Резолвер отвечает кодом `MUTED`.
- **Вход закрыт** (`BANNED`). Вход по паролю и по ссылке отвергается, открытые
  сессии перестают действовать сразу.

**Лимит на записи.** Не больше одной записи в час и двух за скользящие 24 часа,
отдельно для отсутствий и для взносов. Считается по журналу аудита, так что
удалённая запись лимит не возвращает. На администратора и на ввод за участника
(§6.7) лимит не действует. Отказ — код `RATE_LIMITED` с моментом, когда можно
снова.

## 4. Расчётная модель

Ядро продукта. Всё остальное — интерфейс к этим формулам.

### 4.1 Дни присутствия

Для участника `i` и произвольного отрезка `[a, b)`:

```
days(i, a, b) = |{ d ∈ [a, b) :
                   d ∈ [joinedAt(i), leftAt(i))  и
                   d ∉ отсутствия участника i }|
```

**Отсутствия — это отпуск и больничный.** Оба типа влияют на расчёт одинаково: человек не в офисе, воду не пьёт, за эти дни не платит. Тип хранится (`VACATION` / `SICK_LEAVE`) для наглядности в календаре и статистике, но в формулу не входит.

**Удалённая работа в расчёте не учитывается** — сознательное решение. Учитывать её означало бы вести табель присутствия, что превращает бытовое приложение в систему учёта рабочего времени. Если человек работает из дома неделю и это заметно бьёт по справедливости, он оформляет это как отсутствие вручную; регулярную удалёнку модель не покрывает.

Гранулярность — календарный день. Выходные и праздники не учитываются (вода в офисе стоит и в выходные, а усложнение не окупается).

### 4.2 Начальное сальдо

Учёт может начинаться не с нуля: если к моменту запуска в фонде уже есть деньги,
администратор задаёт стартовое состояние на выбранную дату `startDate`:

- `fundOpeningBalance` — сколько денег в фонде на эту дату;
- `openingBalance(i)` — личный баланс каждого участника на эту дату.

**Стартовое состояние не сохраняется, пока не выполнено условие:**

```
Σ openingBalance(i)  ==  fundOpeningBalance
```

Это тот же инвариант §5, применённый к стартовой точке. Если он нарушен, форма
показывает величину расхождения и не даёт продолжить.

Если личные балансы неизвестны, есть кнопка **«Распределить поровну»**:
`openingBalance(i) = fundOpeningBalance / N` с раздачей остатка по правилу §4.6.
Это осознанная потеря точности — она фиксируется в журнале аудита с пометкой
`equal-split`.

**Импорта из Excel нет.** Он был в плане и отменён владельцем 14.08.2026: перенос
истории оказался не нужен. Механизм начальных сальдо остаётся — им пользуется
администратор, заводя участника с ненулевым балансом (§6.7). Все нули — тоже
допустимое стартовое состояние, и именно с него начинается чистый запуск.

**Заведение участника с ненулевым сальдо увеличивает и `fundOpeningBalance`** на
ту же величину, одной транзакцией. Иначе `Σ openingBalance(i)` разойдётся с
начальным состоянием фонда и инвариант §5 сломается в ту же секунду. Смысл
операции при этом честный: у человека есть остаток ровно потому, что его деньги
уже лежат в фонде.

### 4.3 Период потребления заказа

Заказ `k` (дата `t_k`, сумма `C_k`) потребляется в период

```
P_k    = [ t_k , t_{k+1} )     для всех заказов, кроме последнего
P_last = [ t_last , сегодня )  для последнего заказа — период открыт
```

Логика: вода, купленная в день `t_k`, выпивается до следующей закупки.

Оба интервала **полуоткрытые**, как и `days` в §4.1. Это не формальность: при замкнутом
`P_last` день следующей закупки попал бы сразу в два периода и был бы оплачен дважды.
Пример §4.7 (05.06 → 05.07 = 30 дней) считается именно по полуинтервалу.

### 4.4 Распределение стоимости заказа

```
D_k     = Σ_i days(i, P_k)            — все человеко-дни периода
share_k(i) = C_k × days(i, P_k) / D_k  — доля участника i в заказе k
```

Свойство: `Σ_i share_k(i) = C_k` **всегда и точно** (обеспечивается §4.6). Заказ распределяется на 100 % в момент внесения — деньги ушли из фонда, значит балансы должны отреагировать сразу.

Доли внутри открытого периода `P_last` пересчитываются каждый день: пока период идёт, соотношение между участниками уточняется, но сумма остаётся равной `C_last`. Ушедший в отпуск участник со следующего дня начинает получать меньшую долю, а остальные — большую.

**Вырожденный случай.** Если `D_k = 0` (все участники были в отпуске весь период), стоимость делится поровну между участниками, активными на дату `t_k`. Ситуация логируется и показывается администратору как аномалия.

### 4.5 Итоговые формулы

```
Расход(i)  = Σ_k share_k(i)                             по заказам после startDate    
Взносы(i)  = Σ подтверждённых взносов участника i        после startDate    
Прочее(i)  = Σ SETTLEMENT и ADJUSTMENT по участнику i    знаковые суммы

Баланс(i)  = openingBalance(i) + Взносы(i) − Расход(i) + Прочее(i)

Фонд = fundOpeningBalance + Σ CONTRIBUTION
                          + Σ ORDER
                          + Σ SETTLEMENT
                          + Σ ADJUSTMENT
```

**Все операции журнала складываются со своим знаком, без вычитания.** `ORDER` и
`SETTLEMENT` хранятся отрицательными (§2.3), поэтому и в балансе, и в фонде они
прибавляются. Смешивать «знак в поле» с «минусом в формуле» нельзя: именно на этом
инвариант ломается тише всего. `SETTLEMENT` с положительной суммой — ошибка входных
данных и отвергается.

**Триггер «пора скидываться»:** `Баланс(i) < 0`. На главной у такого участника — «Ты должен N ₽». У остальных — «Пока скидываться не надо».

### 4.6 Округление

Доли считаются в копейках. Чтобы `Σ share_k(i)` точно равнялась `C_k`, применяется **метод наибольших остатков**:

1. Для каждого участника считается точная доля как рациональное число.
2. Берётся целая часть в копейках.
3. Нераспределённый остаток (не более `N−1` копеек) раздаётся по одной копейке участникам с наибольшей дробной частью; при равенстве — в порядке `userId` (детерминированно).

Тот же алгоритм используется в кнопке «Распределить поровну» (§4.2).

### 4.7 Пример

Дано: 8 участников, учёт начат 01.06 с фондом 1 000 ₽ (по 125 ₽ на человека). Заказ 05.06 на 3 000 ₽. Сегодня 05.07 — следующего заказа не было. Иван был в отпуске 15 дней из этого периода.

```
Период P₁ = [05.06, 05.07] = 30 дней
Человеко-дней: 7 × 30 + 1 × 15 = 225
Цена дня: 3 000 / 225 = 13,3333 ₽

Иван:      15 × 13,3333 = 200,00 ₽
Остальные: 30 × 13,3333 = 400,00 ₽
Сумма долей: 200 + 7 × 400 = 3 000 ₽ ✓
```

Каждый внёс по 500 ₽ (подтверждено):

| Участник | Начальное | Внёс | Расход | Баланс |
|---|---:|---:|---:|---:|
| Иван | 125 ₽ | 500 ₽ | 200 ₽ | **+425 ₽** |
| Остальные (×7) | 125 ₽ | 500 ₽ | 400 ₽ | **+225 ₽** |

```
Фонд = 1 000 + 8 × 500 − 3 000 = 2 000 ₽
Σ балансов = 425 + 7 × 225 = 2 000 ₽ ✓
```

## 5. Инвариант и самопроверка

```
Σ_i Баланс(i)  ==  Остаток фонда
```

Равенство точное, в копейках, без допусков.

Где проверяется:

1. **Автотест** на генеративных данных: случайные последовательности взносов, заказов, отпусков, входов и выходов участников — инвариант обязан держаться после каждой операции. Это главный тест проекта.
2. **Рантайм-проверка** при каждом пересчёте. Расхождение → запись в лог уровня `error` + баннер администратору.
3. **Раздел «Фонд»** показывает обе величины рядом и зелёную отметку схождения. Это и есть обещанная брифом проверяемость.

Расхождение — всегда баг в коде, а не в данных.

## 6. Экраны

### 6.1 Главная

- Остаток фонда крупно.
- Личный баланс со знаком.
- Статус: «Ты должен N ₽» / «Пока скидываться не надо».
- Кто ещё в минусе (список с суммами) — очередь видна всем.
- Лента последних событий: взносы, заказы, подтверждения.

### 6.2 Мои взносы

Список своих платежей со статусами `PENDING` / `CONFIRMED` / `REJECTED` (у отклонённого виден комментарий администратора).

Статус в таблице показывает значок, а не подпись: своя форма у каждого статуса, подпись и причина отказа — в подсказке по наведению и в скрытой строке для чтения с экрана. На узких экранах, где наведения нет, карточка по-прежнему пишет статус и причину словами.

Форма добавления:
1. Прикрепить фото или скриншот чека.
2. Дата и сумма подставляются автоматически из распознавания (§8), поля остаются редактируемыми, рядом — индикатор уверенности.
3. Отправить → статус `PENDING`.

### 6.3 Все взносы

Таблица: участник, сумма, дата платежа, дата подачи, статус значком (§6.2), кто подтвердил. Фильтры по участнику, периоду, статусу. Ссылка на чек.

### 6.4 Фонд

- Остаток и сходимость инварианта.
- График динамики: поступления и траты по месяцам.
- Таблица балансов всех участников.
- **Раскрытие расчёта:** клик по балансу открывает построчную выкладку — какие взносы, какие заказы, сколько дней присутствия, какая доля. Требование брифа «любое число можно раскрыть» реализуется здесь.

### 6.5 Заказы воды

История: дата, количество бутылей, сумма, поставщик, кто оформил, чек. У каждого заказа — раскрытие распределения по участникам.

**Отметить поставку** — карточка над списком, видная только администратору (§3): дата, сумма, количество бутылей, поставщик, примечание и файл чека. Форма стоит здесь, а не в админ-панели, потому что так думает человек: привезли воду — иду в «Заказы». От места проверка прав не зависит: она живёт в резолвере (ADR-0002), а не в том, кому видна кнопка.

**Чек обязателен.** Поставку нельзя отметить без подтверждения оплаты: деньги уходят из общего фонда, и требование брифа «любое число можно раскрыть» здесь означает не только раскладку по участникам, но и сам документ, по которому эти деньги ушли. Правило держится не разметкой формы, а схемой: `receiptFileId` в `WaterOrderInput` обязателен (§10.2), и мутация без чека отказывает так же, как без суммы.

Колонка `water_orders.receipt_id` при этом остаётся `NULL`-разрешающей: заказы, заведённые до появления этого правила, чеков не имеют, и объявлять их невалидными задним числом было бы неправдой. Список показывает такую строку честно — «чек не приложен», — а не прячет отсутствие.

**Предпросмотр — в двух местах.** В форме, сразу после выбора файла: имя, тип, размер и кнопка, открывающая файл в диалоге прямо из браузера, ничего не отправляя на сервер, — чтобы человек убедился, что приложил тот чек. И в списке заказов: у заказа с чеком кнопка открывает тот же диалог, но уже по адресу `/api/receipts/:id`, и открыть чек может любой участник — деньги потрачены из общего фонда. Картинка показывается как картинка, PDF — встроенным просмотрщиком браузера, с запасной ссылкой «открыть в новой вкладке»: на телефонах PDF во встроенном окне не показывается, и это их норма, а не ошибка.

Форматы, предел размера, хранение и правила выдачи — §8.4.

### 6.6 Отсутствия

Календарь команды на месяц вперёд и назад. Отпуск и больничный различаются цветом и подписью. Форма добавления своих дат с выбором типа. Пересекающиеся отсутствия одного участника запрещены независимо от типа — нельзя быть одновременно в отпуске и на больничном.

### 6.7 Админ-панель

Отдельный раздел, доступный только роли `ADMIN`. Четыре вкладки.

#### Очередь подтверждений

Взносы в статусе `PENDING`. Чек показан рядом с распознанными и введёнными
значениями; расхождение подсвечено. Кнопки «Подтвердить» и «Отклонить
с комментарием». Взносы с низкой уверенностью распознавания — сверху.

#### Участники

Управление составом:

| Действие | Что происходит |
|---|---|
| Добавить | Фамилия, имя, отчество (необязательно), отдел (необязательно, из справочника или новый), почта (необязательно), дата вступления. «Сгенерировать учётные данные» предлагает логин и пароль, их можно поправить. Затем «Создать пользователя», и только после этого появляется карточка с логином, паролем, магической ссылкой и кнопкой «Скопировать» (§7, ADR-0004). Можно сразу задать начальное сальдо (§4.2). |
| Изменить данные | ФИО, отдел, почта. Логин от этого не меняется. |
| Новые учётные данные | Те же два шага, что и при добавлении. Прежние пароль, ссылка и открытые сессии перестают действовать. |
| Ограничение | Без ограничений, только просмотр или вход закрыт (§3). Администратору не ставится. |
| Исключить | Проставляется `leftAt`. Участник **не удаляется**: его взносы и доли в прошлых заказах остаются в истории, иначе поедет инвариант. Он сохраняет доступ и видит свой остаток. |
| Вернуть | Снятие `leftAt` — человек вернулся в офис. |
| Выплатить остаток | Операция `SETTLEMENT` на сумму личного баланса. Сумма в журнале отрицательна (§2.3); положительная — ошибка входных данных и отвергается. Выплатить больше текущего остатка нельзя: это не возврат, а новый долг. |
| Назначить администратором | Смена роли. Последнего администратора разжаловать нельзя. Участника с ограничением сначала нужно освободить. |

**Физического удаления участника нет.** Кнопка «Удалить» соблазнительна, но
удаление человека, за которым числятся взносы и доли в заказах, ломает инвариант
§5 и стирает историю, которую приложение и обещает показывать. Исключение из
состава решает ту же задачу без потери данных.

#### Ввод за участника

Администратор вносит данные за человека, который не может сделать это сам:

- **взнос** — с датой, суммой и, при наличии, чеком;
- **отсутствие** — отпуск или больничный.

Обе записи помечаются полем «внесено администратором» (`entered_by_admin`, §11)
и попадают в журнал аудита с указанием, кто и за кого их создал. Взнос,
внесённый администратором, всё равно проходит подтверждение — иначе исчезает
разделение «внёс» и «проверил».

#### Журнал и корректировки

Журнал аудита с фильтрами по участнику, типу действия и датам. Отсюда же вносятся
корректировки (§2.4) и задаётся стартовое состояние фонда (§4.2).

### 6.9 Дашборд и таймлайн

Главный аналитический экран: как фонд жил во времени и что происходило.

#### Таймлайн

Единая лента событий по всем участникам: взносы, заказы, отсутствия, выплаты,
корректировки. Каждое событие — на своей дорожке, с суммой и участником.
Отсутствия рисуются полосами, а не точками: у них есть длительность.

Под лентой — график остатка фонда за тот же период. Ступени вниз на заказах,
вверх на взносах. Пересечение нуля выделяется: это момент, когда фонд ушёл в минус.

#### Фильтры

| Фильтр | Значения |
|---|---|
| Период | Быстрые: месяц, квартал, год, всё время. «Ручной ввод»: две даты — поля активны только в этом режиме. |
| Гранулярность | Авто (по длине периода), день, неделя, месяц. Влияет на шаг графика и группировку ленты. |
| Участники | Все или выбранные. Поле с тегами: пустой выбор — один тег «Все участники» без крестика. |
| Типы событий | Взносы, заказы, отсутствия, корректировки — по отдельности. Выплаты в фильтре не выбираются и видны в ленте всегда: без них «Потрачено» в сводке расходилось бы со строками ленты. |

Панель фильтров компактная, в три строки: период с датами; участники; типы
событий с шагом. Кнопки «Применить» нет: любое изменение фильтра сразу меняет
адрес, и экран пересчитывается. Поле участников шириной по тегам и переносит
их на следующую строку, упёршись в край. Панель и сводка сворачиваются
(`<details>`); рядом с заголовком сводки стоят границы периода.

При наведении на отметку таймлайна всплывает карточка события: тип, дата и
поля по типу — кто внёс и статус взноса, кто оформил заказ, кто отсутствовал
и сколько дней, кому выплата и кто провёл операцию. При наведении на ступень
графика остатка — остаток на конец шага, изменение за шаг и операции, которые
его сдвинули. Подсказка не единственный носитель: те же события перечислены
списком под графиком.

Выбранный период разделяется между таймлайном и сводкой: цифры сверху всегда
относятся к тому же отрезку, что и график под ними. Диапазон отражается в адресе
страницы, чтобы состоянием экрана можно было поделиться ссылкой.

**Периоду подчиняется всё, фильтрам участников и типов — только лента и сводка.**
График остатка фонда строится по всем движениям денег независимо от них: остаток
кассы один на всех, и «остаток по взносам двух участников» — число, которого
в кассе нет. Показать его значило бы нарушить ограничение ниже.

#### Сводка за период

Поступило, потрачено, изменение остатка, средний расход в день, число заказов,
человеко-дней. Отдельно — самый дорогой заказ и самый длинный период без закупок.

#### Ограничение

Дашборд **только показывает**. Ни одна цифра здесь не является источником истины:
источник — таблицы §6.3–§6.5 и инвариант §5. Расхождение между дашбордом и
таблицами — баг дашборда, а не повод пересчитывать балансы.

### 6.10 Профиль

Адрес `/profile`, внутри оболочки приложения. Ведёт сюда имя в шапке — и значок
рядом с ним, когда имени не видно (§6.11).

- Правка имени и фамилии. Форма та же, что при первом входе (§7), но после
  сохранения остаётся на месте и подтверждает сохранение.
- Учётная запись: логин, почта (если указана), роль, дата вступления в фонд,
  дата выхода, если он был. Всё это меняет только администратор (§6.7).
- Личный баланс со ссылкой на «Мои взносы».
- Выход из учётной записи. Он стоит здесь, а не в навигации (§6.11): действие
  редкое и необратимое, а место в одном ряду с ежедневными ссылками делало его
  случайно нажимаемым. Ищут его там же, где всё остальное про свою запись.

Больше о человеке приложение не знает и знать не должно: список в §7
исчерпывающий.

Первое заполнение имени живёт **не** здесь, а на `/welcome`: оболочка `(app)`
уводит туда участника без имени, и лежи знакомство на `/profile` — редирект
закольцевался бы сам на себя.

### 6.11 Оболочка: навигация и верхняя полоса

Оболочка одна на все экраны — и участника, и администратора. Раньше панель
управления жила отдельной страницей без навигации; теперь это такой же раздел,
и вход в него не отбирает у администратора остальное приложение.

**Разделы сгруппированы.** Их было девять в строку, и шапка вырастала в два
ряда — половина первого экрана уходила на навигацию. Теперь их пять:

| Раздел | Вкладки внутри |
|---|---|
| Главная | — |
| Объявления | — |
| Взносы | Мои взносы · Все взносы |
| Касса | Фонд · Заказы · Отсутствия |
| Дашборд | — |
| Админ-панель (только `ADMIN`) | Очередь · Участники · Ввод за участника · Журнал · Объявления |

Вкладки — настоящие маршруты, а не состояние: ссылкой на «Все взносы» можно
поделиться. Группировка в интерфейсе не обязана повторять дерево адресов:
«Заказы» живут по `/orders`, а принадлежат разделу «Касса» (`/fund`).

**Форма навигации одна, и выбирает её ширина экрана, а не человек.** Раньше
форм было две — боковая панель и строка вкладок, — с кнопкой-переключателем
и запомненным выбором. Выбор стоил трёх компонентов, хранилища, скрипта в
`<head>` и полусотни строк CSS, а сам вопрос «каким меню вы предпочитаете
пользоваться» интерфейс задавать не должен. Панели нет; разделы живут в
верхней полосе, и форм у них две:

| Ширина | Разделы |
|---|---|
| `< md` | полоса значков у нижнего края экрана, закреплённая |
| `md` и шире | строка «значок и подпись» в верхней полосе, посередине |

**Верхняя полоса всегда в один ряд.** Второй ряд — это ровно та высота шапки,
от которой мы уходили. Подпись под значком мы пробовали и отказались: место
под строку находится и без этого, если убрать из полосы название приложения и
имя участника. И то и другое повторяет соседний значок, а подпись раздела не
повторяет ничего — поэтому уступают они, а не разделы. Если разделов однажды
станет больше, чем влезает строкой, полоса уедет по горизонтали.

**Содержимое полосы стоит в том же контейнере, что и содержимое страницы**
(`max-w-6xl`, тот же боковой отступ). Стекло идёт во всю ширину — это край
экрана, — но знак приложения и участник выровнены по той же колонке, что и
всё остальное: иначе они висят снаружи неё и глазу не на что опереться.

- Слева: знак приложения — капля и название «ГИС Пузырик». Название видно
  с `lg` и на телефоне, где разделы уехали вниз и полоса пуста.
- Посередине: разделы, по центру между знаком и участником.
- Справа: тема и участник. Значок участника — крайний справа: он ведёт в
  профиль, а профиль это конец ряда, а не его середина. Имя и роль видны с `xl`.
- **Цифр в полосе нет.** Личный баланс и остаток фонда стояли здесь ради
  ответа «должен или нет» с любого экрана, но занимали середину полосы —
  именно то место, куда встали разделы. Обе цифры встречают человека на
  главной, крупно и с объяснением, и повторять их в каждой строке шапки
  незачем.
- **Выхода в навигации нет.** Он редкий и необратимый, и место рядом с
  ежедневными ссылками делало его случайно нажимаемым; выход живёт в профиле
  (§6.10).

**Узкий экран (`< md`)** уводит разделы к нижнему краю и закрепляет их там:
большой палец достаёт туда не тянясь, чего не скажешь о верхнем крае телефона,
и уход в другой раздел не требует сначала пролистать страницу до конца.
Подписей там нет — шесть слов в строку шириной в телефон нечитаемы, а второй
ряд съел бы экран; название раздела остаётся подсказкой при удержании и
текстом для чтения с экрана. Место под полосу держит отступ содержимого, и
оба размера считаются от одного `env(safe-area-inset-bottom)`: на телефонах с
жестовой полосой значки иначе упираются в неё. Ни одна ссылка при этом не
исчезает: узкий экран меняет форму навигации, а не её состав.

Текущий раздел отмечен стеклянной плиткой, а не одним лишь цветом (§12), и то
же самое сказано читалке через `aria-current`. Вес плитке добавляют кромка,
блик и тень, но не цвет подложки: подложка проверена `check:contrast`, и
подкрасить её значит вывести проверку из-под ног. Блик симметричен — светлый
по верхней и нижней кромке, прозрачный посередине, — так стекло читается
толщиной, а не пятном светлее фона, и текст стоит на ровной подложке. Самый
светлый упор блика равен упору обычного стекла: выше нельзя, иначе проверка
перестаёт описывать эту поверхность. Середина плитки, где блика нет, — её
худший случай, и он проверяется отдельной строкой в `check:contrast`.

### 6.12 Объявления

Сообщения администратора всем участникам: инструкции по пользованию системой и новости про кассу («сменили поставщика», «касса переехала на новый счёт»).

**Объявление — не событие фонда.** Оно не несёт суммы, не участвует в расчёте балансов и не попадает ни в журнал операций, ни на таймлайн §6.9. Причина не только в чистоте модели: типы событий закреплены за слотами палитры графиков (§12), пятью цветами, и шестой тип потребовал бы шестого цвета там, где различимость уже на пределе.

В ленте главной объявление тем не менее стоит рядом с заказами и взносами: человек читает там одну хронику кассы, и «сменили поставщика» — её часть. Сводятся они **на уровне экрана** (`src/lib/view/feed.ts`), а не в модели: у элемента ленты свой тип, `EVENT_KINDS` не трогается, дашборд объявлений не показывает.

Одна сущность на оба жанра. Инструкция и новость отличаются только сроком жизни, и разводить их в две таблицы незачем: закреплённое объявление (`pinned`) висит наверху и не тонет — это и есть инструкция; обычное уходит вниз по дате публикации.

**Закреплённых не больше трёх.** Три инструкции наверху ещё читаются, десять — уже второй список, в котором снова всё тонет. Лимит считается по объявлениям вне архива, черновики входят в него: опубликованный черновик не должен молча превышать предел. Попытка закрепить четвёртое отвергается с просьбой сначала открепить одно из закреплённых, и их заголовки перечислены прямо в сообщении. Закрепить и открепить можно в любой момент — отдельной кнопкой на карточке объявления, не открывая правку текста. Уходя в архив, объявление открепляется: иначе возврат из архива мог бы превысить предел в обход проверки.

Состояния:

| | |
|---|---|
| Черновик | `published_at IS NULL` — виден только администратору |
| Опубликовано | видно всем участникам |
| В архиве | `archived_at IS NOT NULL` — снято с глаз, но не удалено: на запись ссылается журнал аудита |

**Непрочитанное** считается от `users.announcements_seen_at` — момента последнего захода участника в раздел. Отдельной таблицы «кто что прочитал» нет: для полутора десятков человек она стоила бы дороже пользы. Отметка ставится по самой свежей публикации, а не по «сейчас», иначе объявление, вышедшее между открытием списка и записью, погасло бы непрочитанным.

Где видно:

- **раздел «Объявления»** — весь список: закреплённые сверху, дальше по дате;
- **главная (§6.1)** — в общей ленте событий, по дате публикации: заголовок и первые слова, по нажатию раскрывается целиком (`<details>`, без состояния в React); непрочитанное помечено значком «Новое», но отметку «прочитано» главная не ставит — иначе человек увидел бы заголовок и никогда не прочёл текст;
- **шапка (§6.11)** — счётчик непрочитанного на значке раздела;
- **админ-панель (§6.7)** — пятая вкладка: создание, правка, закрепление, архив.

Правка объявления разрешена: опечатку в инструкции нужно уметь исправить, и правило неизменяемости журнала (§2.3) сюда не относится — оно про `fund_transactions`. Взамен каждая правка ложится в `audit_log` со снимком «до» и «после», а дата публикации при правке **не сдвигается**: иначе исправленная опечатка вспыхнула бы у всей команды как свежая новость.

Разметки в тексте нет. Распознаются ровно три вещи: абзац (пустая строка), маркированный список (`- `) и нумерованный (`1. `). Ни Markdown-библиотеки, ни `dangerouslySetInnerHTML`: администратор пишет текст в поле ввода, и его содержимое — ввод, а не доверенная разметка.

**Картинка.** К объявлению можно приложить одну картинку — PNG, JPEG, GIF или WebP, до 2 МБ.

- **Тип определяется по сигнатуре файла**, а не по расширению и не по тому, чем файл назвался в форме. `Content-Type` из браузера — такой же ввод, как и всё прочее: страница HTML, названная `image/png` и отданная обратно с этим заголовком, выполнилась бы в чужом браузере. Расхождение объявленного типа с настоящим — отказ.
- **Описание (`alt`) обязательно** вместе с файлом: без него картинка молчит для тех, кто её не видит (§12). Правило стоит и в базе отдельным `CHECK`.
- **Размеры хранятся** рядом с описанием: зная их, страница резервирует место и не дёргается, когда картинка догрузится.
- **Байты лежат в базе**, отдельной таблицей `announcement_images`. Решение по хранилищу чеков (открытый вопрос №6) этим не предрешается: адрес выдачи ведёт на приложение (`/api/notices/:id/image`), а не на хранилище, ровно как `Receipt.url` (§8). Отдельная таблица нужна потому, что Prisma выбирает все колонки, и `BYTEA` внутри `announcements` означал бы, что список объявлений на каждом экране вычитывает мегабайты, которые ему не нужны.
- **Выдача закрыта входом.** Касса — внутреннее приложение, и снимок экрана с фамилиями должников не должен открываться по ссылке кому угодно. Картинку черновика и архива видит только администратор; всем остальным — тот же 404, что и у несуществующей.

Адресных сообщений одному участнику здесь нет: напоминание «пора скидываться» — это уведомление, и его место в §14, этап 8 (Telegram).

## 7. Аутентификация

Вход по логину и паролю, которые выдаёт администратор (ADR-0004). Своей
регистрации нет. Под заголовком — описание фонда, под формой сказано, что
логин и пароль предоставляются администратором по запросу, и стоит кнопка
«Присоединиться к водопою» — она
ведёт в Telegram администратора (`ADMIN_TELEGRAM_URL`; без переменной кнопки
нет).

Схему адреса дописывает приложение, а не тот, кто заполнял переменную:
`t.me/ivanov` без неё браузер считает путём внутри сайта, и кнопка открывает
свою же страницу 404. Разрешены только `http` и `https`.

Подпись поля — маленькое стёклышко над ним, тот же приём, что отмечает
выбранный раздел в шапке (§6.11): одна идея на два места, а не два похожих.
Поля подпись не касается: наползающая плашка закрывает кусок рамки и спорит
с ней за внимание — рамка говорит «сюда пишут», подпись говорит, как это
называется. В фокусе подпись подхватывает кольцо поля.

Подпись блочная, а не строчная, и это не вкусовщина: у строчного элемента
высота считается межстрочным интервалом родителя, а не собственным, — ровно
поэтому «Логин» и «Пароль» разъезжались по высоте при одинаковой разметке.

У поля пароля есть глаз — показать набранное. Пароль выдаёт администратор, и
набирают его с бумажки или из сообщения, вслепую и почти всегда с ошибкой;
дать посмотреть дешевле, чем заставлять вводить заново. Показ всегда
начинается выключенным.

1. **Логин** собирается из ФИО латиницей: первая буква имени, первая буква
   отчества (если есть) и фамилия, через точку: `e.v.kondobarov`. Если логин
   занят, к нему добавляется число: `e.kondobarov2`. Администратор может его
   поправить: допустимы латиница, цифры, точка и дефис, от 3 до 40 символов.
2. **Пароль** — 12 случайных символов без похожих знаков, поправить можно не
   короче чем до 8. В базе лежит только отпечаток scrypt с солью. В открытом
   виде пароль виден один раз, в карточке после создания.
3. **Магическая ссылка** `/l/<токен>` действует 7 дней, многоразовая, у
   участника одна. В базе хранится HMAC токена. Страница ссылки входит только
   по кнопке «Войти», чтобы превью в мессенджерах не получало сессию.
4. **Отказы:** «нет такого логина», «пароль не выдан» и «неверный пароль»
   неразличимы. После 10 неудач подряд вход блокируется на 15 минут. О бане
   сообщается только после верного пароля.
5. **Сессия** — httpOnly-cookie на 30 дней с моментом выдачи. Перевыпуск
   учётных данных и бан отзывают все прежние сессии участника
   (`users.sessions_valid_after`).
6. Участник, заведённый до выдачи логинов без имени, при входе попадает на
   `/welcome`. Остальным ФИО вводит администратор.

Первому администратору пароль выдаёт команда `npm run credentials -- <логин>`:
в панели без входа это не сделать.

Хранимые персональные данные: фамилия, имя, отчество (необязательно), логин,
отдел (необязательно), рабочий email (необязательно). Больше ничего. Это
сознательное ограничение из брифа, позволяющее не выстраивать полноценную
политику обработки персональных данных.

Под Telegram (этап 8) остаётся таблица `identities` с полями `provider` и
`providerId`. Саморегистрация через бота по ФИО пойдёт той же генерацией
учётных данных.

## 8. Чеки: файл и распознавание

Чек живёт двумя жизнями: как файл, который человек прикладывает и открывает
(§8.4), и как источник данных, предзаполняющий форму (§8.1–8.3). Первая
появляется вместе с формой поставки (§6.5), вторая — на этапе 6.

### 8.1 Провайдер-агностичный слой

Приложение не знает, кто именно распознаёт чек. Оно знает интерфейс.

```ts
// src/lib/receipts/types.ts

export type ReceiptInput = {
  data: Buffer;
  mediaType: 'image/jpeg' | 'image/png' | 'image/webp' | 'application/pdf';
};

export type Confidence = 'high' | 'medium' | 'low';

export type ReceiptExtraction = {
  paidAt: string | null;        // ISO 8601, дата платежа
  amountKopecks: number | null; // сумма в копейках
  payerHint: string | null;     // имя отправителя, если видно
  confidence: Confidence;
  notes: string;                // что мешало распознать
  provider: string;             // идентификатор реализации
  rawResponse: unknown;         // сырой ответ, для отладки и аудита
};

export interface ReceiptExtractor {
  readonly id: string;
  extract(input: ReceiptInput): Promise<ReceiptExtraction>;
}
```

Реализации:

| Реализация | Роль |
|---|---|
| `ClaudeReceiptExtractor` | По умолчанию. Claude Opus 5, vision + структурированный вывод. |
| `ManualReceiptExtractor` | Заглушка: возвращает пустое извлечение с `confidence: 'low'`. Используется, когда ключ API не задан, и в тестах. |

Выбор реализации — через фабрику по переменной окружения `RECEIPT_EXTRACTOR`. Замена провайдера не затрагивает ни один слой выше `src/lib/receipts/`.

### 8.2 Реализация на Claude

```ts
// src/lib/receipts/claude.ts
import Anthropic from '@anthropic-ai/sdk';

const client = new Anthropic();

const RECEIPT_SCHEMA = {
  type: 'object',
  properties: {
    paidAt:     { type: ['string', 'null'], description: 'Дата платежа в формате YYYY-MM-DD' },
    amount:     { type: ['number', 'null'], description: 'Сумма платежа в рублях' },
    payerHint:  { type: ['string', 'null'], description: 'Имя отправителя, если видно на чеке' },
    confidence: { type: 'string', enum: ['high', 'medium', 'low'] },
    notes:      { type: 'string', description: 'Что помешало распознать, если что-то помешало' },
  },
  required: ['paidAt', 'amount', 'payerHint', 'confidence', 'notes'],
  additionalProperties: false,
} as const;

const PROMPT = `Это чек или скриншот банковского перевода. Извлеки дату платежа и сумму.

Даты в российских чеках чаще записаны как ДД.ММ.ГГГГ — приведи к YYYY-MM-DD.
Если на чеке несколько сумм, выбери сумму перевода, а не комиссию и не остаток по счёту.
Если значение не читается, верни null и объясни причину в notes. Не угадывай.`;

export const claudeReceiptExtractor: ReceiptExtractor = {
  id: 'claude-opus-5',

  async extract({ data, mediaType }) {
    const response = await client.messages.create({
      model: 'claude-opus-5',
      max_tokens: 2048,
      output_config: {
        effort: 'medium',
        format: { type: 'json_schema', schema: RECEIPT_SCHEMA },
      },
      messages: [{
        role: 'user',
        content: [
          { type: 'image', source: { type: 'base64', media_type: mediaType, data: data.toString('base64') } },
          { type: 'text', text: PROMPT },
        ],
      }],
    });

    if (response.stop_reason === 'refusal') {
      return emptyExtraction('claude-opus-5', 'Модель отклонила запрос');
    }

    const block = response.content.find((b) => b.type === 'text');
    const parsed = JSON.parse(block!.text);

    return {
      paidAt: parsed.paidAt,
      amountKopecks: parsed.amount === null ? null : Math.round(parsed.amount * 100),
      payerHint: parsed.payerHint,
      confidence: parsed.confidence,
      notes: parsed.notes,
      provider: 'claude-opus-5',
      rawResponse: parsed,
    };
  },
};
```

Заметки по API, важные для реализации:

- `output_config.format` со схемой `json_schema` гарантирует валидный JSON — парсер с ретраями не нужен.
- `additionalProperties: false` и полный список в `required` обязательны для строгой схемы.
- На Opus 5 параметры `temperature`, `top_p`, `top_k` не принимаются — вернётся ошибка 400. Поведение задаётся промптом.
- `stop_reason: 'refusal'` приходит с HTTP 200. Проверять его нужно **до** чтения `content`.
- `effort: 'medium'` подобран под задачу: механическое извлечение из изображения. Если чеки с рук читаются плохо — поднять до `high`.

### 8.3 Правила использования результата

- Распознавание **никогда не создаёт взнос автоматически**. Оно только предзаполняет форму.
- Пользователь видит и правит оба поля перед отправкой.
- Администратор видит и чек, и распознанные значения, и введённые пользователем — расхождение подсвечивается.
- `confidence: 'low'` помечает взнос флагом «требует внимания» в очереди администратора.
- `rawResponse` хранится: он нужен, когда через полгода придётся разбираться, откуда взялась дата.

### 8.4 Файл чека: форматы, хранение, выдача

**Форматы.** PDF и картинки — PNG, JPEG, WebP, GIF. Предел — 5 МБ: чек это
снимок экрана банковского перевода или квитанция, а не фотоальбом.

**Тип определяется по сигнатуре файла**, а не по расширению и не по тому, чем
файл назвался в форме (`inspectReceiptFile` в `src/lib/receipts/file.ts` —
чистая функция, как `inspectImage` для картинок объявлений). `Content-Type` из
браузера — такой же ввод, как и всё прочее: страница HTML, названная
`application/pdf` и отданная обратно с этим заголовком, выполнилась бы в чужом
браузере. Расхождение объявленного типа с настоящим — отказ.

**Байты лежат в базе**, отдельной таблицей `receipt_files` (§11). Обоснование
и отвергнутые варианты — [ADR-0003](./decisions/0003-receipt-files-live-in-the-database.md).
Колонка `receipts.storage_key` означает место хранения: `db:<receipt_id>`
сегодня, `s3:<bucket>/<key>` в тот день, когда чеков станет много. Клиент о
хранилище не знает: `Receipt.url` ведёт на приложение.

**Загрузка идёт формой в серверное действие** (ADR-0002): действие разбирает
`FormData`, проверяет байты и вызывает мутацию `uploadReceipt`, а затем ту, что
создаёт запись с `receiptFileId`. Эндпоинт `POST /api/upload` из §10.3
понадобится на этапе 6, когда распознавание начнёт работать до отправки формы;
до тех пор он не реализован.

**Выдача — `GET /api/receipts/:id`,** вход обязателен. Чек виден, если он
привязан к заказу (заказы внутри приложения открыты всем участникам) или к
взносу — его автору и администратору. Ни к чему не привязанный чек — 404 для
всех: это мусор незавершённой отправки. Ответ несёт `ETag` (файл неизменяем),
`X-Content-Type-Options: nosniff` и `Content-Disposition: inline`;
`?download=1` превращает его в `attachment`. Для PDF добавляется
`Content-Security-Policy: sandbox`: встроенный просмотрщик умеет исполнять
JavaScript из документа, а отдаётся документ со своего домена.

## 9. Раздел «Помощник»

Чат-помощник с контекстом проекта и текущих данных. Задачи: объяснять, как считается баланс, и независимо перепроверять расчёты.

### 9.1 Сценарии

1. **«Почему я должен 340 ₽?»** — помощник разбирает баланс по составляющим: начальное сальдо, взносы, доли в конкретных заказах, влияние отпуска.
2. **«Как вообще считается?»** — объяснение модели §4 человеческим языком, с примером на текущих данных.
3. **«Проверь, всё ли сходится»** — режим аудита: помощник получает журнал операций и **пересчитывает балансы самостоятельно**, затем сравнивает со значениями приложения. Расхождение — сигнал о баге.
4. **«Кому сейчас скидываться?»** — сводка по очереди.

### 9.2 Устройство контекста

Системный промпт состоит из двух частей с разной изменчивостью — это важно для кеширования:

| Часть | Содержимое | Изменчивость |
|---|---|---|
| Стабильная | Описание продукта, полная расчётная модель §4, инвариант §5, правила общения | Меняется с релизом |
| Волатильная | Текущий снимок данных: участники, фонд, заказы, взносы, отпуска, балансы — в JSON | Меняется постоянно |

Стабильная часть помечается `cache_control: { type: 'ephemeral' }`. На Opus 5 минимальный кешируемый префикс — 512 токенов; описание модели его превышает, так что кеш будет работать с первого дня. Волатильная часть идёт **после** точки кеширования, иначе кеш сбрасывается на каждом запросе.

```ts
const response = await client.messages.create({
  model: 'claude-opus-5',
  max_tokens: 8000,
  system: [
    { type: 'text', text: PRODUCT_AND_CALCULATION_MODEL, cache_control: { type: 'ephemeral' } },
  ],
  output_config: { effort: 'high' },
  messages: [
    { role: 'user', content: `Текущее состояние:\n\n${JSON.stringify(snapshot)}\n\nВопрос: ${question}` },
  ],
  stream: true,
});
```

Ответ стримится в интерфейс.

### 9.3 Ограничения

- **Только чтение.** У помощника нет инструментов записи. Он не может создать взнос, подтвердить платёж или изменить баланс.
- **Данные не приватные.** Помощник видит ровно то, что и так видит любой участник в интерфейсе. Дополнительной утечки нет по построению.
- **Лимит:** 20 сообщений на участника в сутки. Защита от случайного разорения на токенах.
- **Дисклеймер в интерфейсе:** источник истины — таблицы и инвариант, а не ответ помощника. Раздел вспомогательный.
- История диалога хранится в БД по участнику: удобно для отладки промпта.

## 10. GraphQL API

### 10.1 Зачем здесь GraphQL

Учебная цель проекта. На этой предметной области хорошо видны именно те свойства, ради которых GraphQL и берут:

- **Один эндпоинт вместо десятка.** Главная, «Фонд» и «Все взносы» тянут пересекающиеся данные разными срезами — в REST это три ручки, здесь один запрос с разным набором полей.
- **Клиент выбирает поля.** Главной нужен только `myBalance.amount`, экрану «Фонд» — вся раскладка. Один и тот же тип, разный объём ответа.
- **Сквозная типизация.** Схема → codegen → типы TypeScript на клиенте и сервере. Переименовал поле в схеме — компилятор показал все места, где оно используется.
- **Проблема N+1 и DataLoader.** Запрос `contributions { user { firstName } }` на 200 взносов без батчинга даст 200 запросов к базе. Это классическая ловушка GraphQL, и здесь она возникнет естественным образом — хороший повод разобраться с `DataLoader`.
- **Что GraphQL не даёт бесплатно:** кеширование HTTP, загрузку файлов, ограничение сложности запроса. Файл чека приходит формой в серверное действие (§8.4), а GraphQL получает байты в base64 либо готовый `receiptFileId` — это нормальная практика, а не костыль. Отдельный `POST /api/upload` появится на этапе 6, когда распознавание начнёт работать до отправки формы.

### 10.2 Схема

```graphql
scalar Date       # YYYY-MM-DD
scalar DateTime   # ISO 8601
scalar Money      # копейки, целое число

enum Role               { PARTICIPANT ADMIN }
enum ContributionStatus { PENDING CONFIRMED REJECTED }
enum Confidence         { HIGH MEDIUM LOW }
enum AbsenceType        { VACATION SICK_LEAVE }

# ─── Участники ───────────────────────────────────────────

type User {
  id: ID!
  email: String!
  firstName: String
  lastName: String
  role: Role!
  joinedAt: Date!
  leftAt: Date
  isActive: Boolean!
  openingBalance: Money!
  balance: Balance!
  absences: [Absence!]!
  contributions(status: ContributionStatus): [Contribution!]!
}

type Balance {
  user: User!
  amount: Money!            # < 0 → участник должен
  owes: Boolean!
  breakdown: BalanceBreakdown!
}

"Раскрытие баланса — то, что показывает экран «Фонд» по клику"
type BalanceBreakdown {
  openingBalance: Money!
  contributionsTotal: Money!
  expensesTotal: Money!       # положительная величина: сумма долей в заказах
  settlementsTotal: Money!    # знаковая: выплата отрицательна (§2.3)
  adjustmentsTotal: Money!    # знаковая: корректировка бывает в обе стороны
  orderShares: [OrderShare!]!
}

type OrderShare {
  order: WaterOrder!
  daysPresent: Int!
  totalPersonDays: Int!
  share: Money!
}

# ─── Фонд ────────────────────────────────────────────────

type Fund {
  balance: Money!
  openingBalance: Money!
  startDate: Date
  defaultContribution: Money!
  balancesSum: Money!        # для проверки инварианта
  isConsistent: Boolean!     # balance == balancesSum
  monthlyStats: [MonthlyStat!]!
}

type MonthlyStat {
  month: String!             # YYYY-MM
  contributions: Money!
  orders: Money!             # отрицательная: деньги ушли из фонда (§2.3)
  endBalance: Money!
```

### 10.3 Технические решения

| Аспект | Решение |
|---|---|
| Сервер | GraphQL Yoga в Route Handler Next.js (`app/api/graphql/route.ts`) |
| Клиент | urql или Apollo Client, React Server Components — для первичной загрузки |
| Типизация | GraphQL Code Generator: схема → типы + типизированные хуки |
| N+1 | DataLoader на `User`, `Receipt`, `OrderShare` |
| Авторизация | Проверка роли в резолверах через контекст; `pendingContributions`, `auditLog` и админ-мутации — только `ADMIN` |
| Ограничение сложности | `graphql-depth-limit` + лимит стоимости запроса |
| Ошибки | Типизированные коды в `extensions.code`, не строки |
| Загрузка файлов | Формой в серверное действие → `uploadReceipt` (§8.4); `POST /api/upload` — этап 6 |

`EXCLUDE USING gist` на `absences` запрещает пересекающиеся отсутствия одного участника на уровне базы — независимо от типа. Ограничение намеренно не учитывает `type`: одновременно быть в отпуске и на больничном нельзя, а если бы такая запись прошла, день вычелся бы дважды и инвариант поехал. Правило стоит в базе, а не в приложении, чтобы его нельзя было обойти прямой записью.

## 12. Дизайн

- Водная палитра: глубокий синий, голубой, белый. Акцент — бирюзовый.
- Светлая и тёмная темы обязательны, через CSS-переменные. До первого выбора тема определяется по `prefers-color-scheme`; переключатель — одна иконка на два состояния, светлое и тёмное, и выбор сохраняется.
- Главный экран должен читаться без чтения: цвет и размер числа отвечают на вопрос «должен или нет» раньше текста. Долг — тёплый акцент, положительный баланс — спокойный синий.
- Цвет никогда не единственный носитель смысла: рядом всегда знак или подпись.
- Mobile-first. Таблицы на узких экранах превращаются в карточки, а не в горизонтальный скролл.
- Компоненты: Tailwind CSS + shadcn/ui.
- Контраст не ниже AA в обеих темах.

### 12.1 Визуальный язык: вода и стекло

- **Фон — толща воды, а не заливка.** На базовом цвете лежат три размытых пятна
  света (`--depth-1…3`), заданные на `<html>`: фон корневого элемента
  распространяется на холст, поэтому покрывает экран и не едет при прокрутке.
  `<body>` обязан оставаться прозрачным — иначе он закрасит воду собой.
- **Поверхности стеклянные** (`.glass`, `.glass-strong`, `.glass-soft`):
  полупрозрачный цвет карточки, размытие подложки и светлый блик по верхней
  кромке. Три градации — карточка, шапка и диалог, плитка внутри карточки.
- **Прозрачность подчинена контрасту, а не наоборот.** Доля карточки в стекле
  высокая (78–92%): галерейные 15–30% пускают фон в буквы и рушат AA. Проверку
  делает `npm run check:contrast` — он складывает все слои (фон, три пятна,
  стекло, блик) и считает контраст итоговой подложки с каждым цветом текста.
  Порог тот же, что и у палитры: 4.5:1 для текста, 3:1 для границ.
- **Текст на голом фоне проверяется наравне со стеклом.** Заголовки экранов и
  пояснения под ними стоят прямо на воде, без подложки, и у этой пары свой
  худший случай. Проверяются ровно те цвета,
  которые там действительно стоят; появится на фоне сумма или поле ввода —
  список в скрипте надо расширить, а не радоваться зелёной проверке.
- **Стекло надстраивается, а не предполагается.** Непрозрачная подложка —
  значение по умолчанию; размытие включается через `@supports` там, где
  браузер умеет `backdrop-filter`. Системные просьбы
  `prefers-reduced-transparency` и режим `forced-colors` возвращают
  непрозрачные поверхности и системные цвета.
- **Градиенты** — на кнопке основного действия, знаке приложения и названии.
  Оба конца каждого градиента проверяются на контраст по отдельности: «в
  среднем проходит» означает, что на одном краю текст не читается.
- **Значки — Lucide, один набор и одна толщина линии.** Значок всегда
  дублирует стоящую рядом подпись и потому скрыт от чтения с экрана
  (`aria-hidden`). Значок, которому нечего дублировать, обязан получить
  текстовую подпись, а не остаться немым.
- **Графики стоят на непрозрачной поверхности** (`.plot-surface`). Палитра §12
  проверена против цвета карточки; на просвечивающей подложке эта проверка
  перестаёт что-либо гарантировать.
- **Движение — только отклик на действие.** Наведение и нажатие, 150–200 мс;
  нажатие отвечает масштабом, а не смещением, чтобы соседние элементы не
  съезжали. `prefers-reduced-motion` движение отключает.

## 12а. Правила фронтенда

**Пишем на возможностях React 19, а не React 18.** Формы — через `useActionState`
и `<form action>`, индикаторы ожидания — `useFormStatus`, мгновенный отклик —
`useOptimistic`, чтение данных — серверные компоненты с `await` вместо `useEffect`.
`'use client'` ставится только там, где нужны события, состояние или браузерные API.
Полная таблица соответствий «задача → современный приём» — в `CLAUDE.md`.

Из серверных компонентов GraphQL вызывается напрямую через слой данных, без
HTTP-запроса к собственному `/api/graphql`: сеть внутри одного процесса — чистые
потери. HTTP-эндпоинт остаётся для клиентских компонентов и внешних потребителей.

Управление составом участников, ввод данных за участника, начальные сальдо. См. §6.7.

### Этап 5 — Интерфейс
Все экраны, дашборд с таймлайном (§6.9), раскрытие расчёта, мобильная вёрстка.

### Этап 6 — Чеки
`ReceiptExtractor`, реализация на Claude, предзаполнение формы, флаг «требует внимания».

### Этап 7 — Помощник
Промпт, снимок данных, кеширование, стриминг, режим аудита, лимиты.

### Этап 8 — Telegram (отдельный этап после запуска)
Бот, Mini App, вход через Telegram, уведомления. Саморегистрация: человек
пишет боту ФИО, ему генерируются логин и пароль тем же способом, что в админке
(§7).

## 14а. Демонстрационные данные

Реальных участников ещё нет, а видеть экраны с настоящей историей нужно уже
на этапе разработки. `npm run db:seed:mock` наполняет базу полугодом жизни офиса:
восемь участников, девять заказов, взносы, отпуска и больничные, очередь на
подтверждение, один должник и один вышедший из состава.

Данные детерминированы — один прогон даёт ту же картинку, что и предыдущий.
Иначе отладка и скриншоты разъезжались бы от запуска к запуску.

Набор намеренно содержит неудобные случаи, а не только ровные: участник, пришедший
в середине периода; вышедший из состава с остатком на балансе; человек, который
отстал со взносами и должен светиться должником; отпуск, накрывающий границу
заказа. На гладких данных ошибки расчёта не видны.

Скрипт отказывается работать при `NODE_ENV=production` и стирает взносы, заказы,
отсутствия и журнал операций перед наполнением. Боевой `npm run db:seed` создаёт
только настройки фонда и первого администратора.

## 15. Тестирование

| Уровень | Что покрывает |
|---|---|
| Генеративные | Инвариант `Σ балансов == фонд` на случайных последовательностях операций. **Главный тест проекта.** |
| Модульные | `calc/`: дни присутствия, доли, округление, вырожденные случаи, границы отсутствий, вход и выход участника |
| Интеграционные | GraphQL: права по ролям, модерация взносов, повторная установка сальдо |
| E2E | Ключевые сценарии: вход → подача взноса → подтверждение → изменение баланса |
| Ручные | Распознавание чеков на реальной выборке; качество ответов помощника |

Обязательные модульные случаи: заказ в первый день отсутствия; отсутствие, накрывающее период целиком; отпуск и больничный встык у одного участника; участник, вошедший в середине периода; период с нулём человеко-дней; распределение остатка копеек между 3, 7 и 8 участниками.

# WaterDrinkers

Учёт офисной кассы на бутилированную воду. Прозрачно показывает, кто сколько внёс,
сколько потрачено, сколько осталось в фонде и кому пора скидываться.

**Стек:** Next.js (App Router, TypeScript) · GraphQL (Yoga) · PostgreSQL (Prisma) · Tailwind + shadcn/ui
**Язык общения:** русский. Код, имена файлов, коммиты — английский.

## Незыблемые правила

Нарушение любого из них — баг, а не компромисс.

1. **Инвариант.** `Σ балансов всех участников == остаток фонда`, точно, всегда.
   Расхождение — всегда ошибка в коде. Проверяется генеративными тестами.
2. **Деньги — только целые копейки** (`BIGINT` в БД, `number` в копейках в коде).
   Числа с плавающей точкой в денежных расчётах запрещены: они ломают инвариант.
3. **Округление долей — метод наибольших остатков** (`src/lib/calc/shares.ts`).
   Сумма долей обязана совпадать со стоимостью заказа до копейки.
4. **Журнал операций неизменяем.** Записи `fund_transactions` не редактируются и
   не удаляются. Ошибка исправляется компенсирующей операцией `ADJUSTMENT`.
5. **Ядро расчёта — чистые функции.** В `src/lib/calc/` нет обращений к базе,
   сети и глобальному состоянию. Только вход → выход.
6. **Взнос влияет на баланс только после подтверждения администратором.**
   Взнос, который внёс сам администратор (`RECORDED`), подтверждён самим
   фактом ввода — ADR-0005.
7. **Персональные данные:** храним только фамилию, имя, отчество (необязательно),
   логин, отдел (необязательно) и рабочий email (необязательно) — решение
   ADR-0004. Ничего сверх этого не добавлять без явного решения.

## React 19 — писать на современных возможностях

Проект на React 19 и Next.js 16. Пиши так, как пишут на React 19, а не так, как
писали на 18. Старые приёмы работают, но порождают лишний код и лишние состояния.

| Задача | Как делать | Чего не делать |
|---|---|---|
| Отправка формы | `<form action={fn}>` + `useActionState` | `onSubmit` с `preventDefault`, ручной `fetch` |
| Индикатор загрузки | `useFormStatus` внутри формы | ручной флаг `busy` в `useState` |
| Мгновенный отклик до ответа сервера | `useOptimistic` | ручная подмена состояния и откат |
| Мутация данных | Server Action (`'use server'`) | клиентский `fetch` к своему же API |
| Чтение промиса в компоненте | `use(promise)` | `useEffect` + `useState` |
| Проброс `ref` | обычный проп `ref` | `forwardRef` |
| Загрузка данных | Server Component + `await` | `useEffect` с запросом на монтировании |
| Заголовок и мета | `<title>`, `<meta>` прямо в компоненте | ручная возня с `head` |
| Мемоизация запроса за один рендер | `cache()` из `react` | самодельные словари-кеши |

**Клиентский компонент — исключение, а не норма.** `'use client'` ставится только
там, где нужны обработчики событий, состояние или браузерные API. Всё остальное —
серверные компоненты: они не едут в бандл и ходят в базу напрямую.

**GraphQL из серверных компонентов вызывается напрямую** через резолверы или
слой данных, без HTTP-запроса к собственному `/api/graphql`. Сеть внутри одного
процесса — чистые потери. HTTP-эндпоинт остаётся для клиентских компонентов
и внешних потребителей.

## Порядок работы

- Ядро расчёта пишется до интерфейса. Если арифметика неверна, остальное бессмысленно.
- Каждая законченная единица работы — отдельный коммит.
- Изменил поведение — обнови тест. Изменил решение из спецификации — обнови `docs/SPEC.md`.
- Не переходить к следующему этапу, пока тесты текущего не зелёные.

## Команды

```bash
npm run dev              # дев-сервер
npm test                 # тесты
npm run test:watch       # тесты в watch-режиме
npm run typecheck        # проверка типов
npm run lint             # линтер
npx prisma migrate dev   # миграция БД
npx prisma studio        # просмотр данных
npm run codegen          # генерация типов из GraphQL-схемы
npm run check:contrast   # контраст текста на стеклянных поверхностях (§12.1)
```

*(скрипты появляются на этапе 0; до него команд нет)*
